The app exposes per-queue BullMQ job counts in Prometheus text format so a scraper can track queue depth by state (`waiting`, `active`, `completed`, `failed`, `delayed`, `paused`).

## Endpoint (self-hosted only)

```
GET /v1/worker-machines/queue-metrics/prometheus/:queueName
```

- Available on self-hosted Community and Enterprise. Not registered on Cloud.
- `:queueName` is optional and defaults to `workerJobs` (the shared queue). Pass a worker-group queue name (e.g. `platform-<groupId>-jobs`) to scrape a dedicated queue.
- Auth: `Authorization: Bearer <platform API key>` (an `sk-...` key created under platform admin). Platform admin user tokens work too.
- Returns `text/plain`. Responds `404` if the queue has not been initialized on this app instance.

### Example

```bash
curl -H "Authorization: Bearer $PLATFORM_API_KEY" \
  https://your-instance.example.com/api/v1/worker-machines/queue-metrics/prometheus/workerJobs
```

```
# HELP bullmq_job_count Number of jobs in the queue by state
# TYPE bullmq_job_count gauge
bullmq_job_count{queue="workerJobs", state="waiting"} 0
bullmq_job_count{queue="workerJobs", state="active"} 3
bullmq_job_count{queue="workerJobs", state="completed"} 0
bullmq_job_count{queue="workerJobs", state="failed"} 1
bullmq_job_count{queue="workerJobs", state="delayed"} 0
```

<Note>
Bearer auth works with standard scraper config: Prometheus `authorization.credentials`, Azure managed Prometheus `bearer_token_file`, Grafana Alloy `bearer_token`. No header-injecting proxy is needed.
</Note>

Metrics come from BullMQ's built-in `Queue.exportPrometheusMetrics()`. Each queue only reports the states it holds on the app instance being scraped; in a multi-worker-group deployment, scrape each group's queue by name (`platform-<groupId>-jobs` / `project-<groupId>-jobs`). A JSON variant with `waiting`/`active` counts only lives at `GET /v1/worker-machines/queue-metrics` (all editions, used for KEDA autoscaling).

## Sandbox metrics (self-hosted only)

```
GET /v1/worker-machines/sandbox-metrics/prometheus
```

- Same availability and auth as the queue endpoint above.
- Reports every online worker the platform can see, from the worker's latest heartbeat. All metrics are gauges.

| Metric | Labels | Meaning |
| --- | --- | --- |
| `activepieces_sandbox_memory_usage_bytes` | `worker_id`, `host`, `box_id` | Total resident memory of the sandbox process and its children: V8 heap plus buffers, native memory and the Node runtime. This is what counts against the container memory limit |
| `activepieces_sandbox_heap_used_bytes` | `worker_id`, `host`, `box_id` | V8 JS heap in use in the sandbox engine process. The only part capped by `AP_SANDBOX_MEMORY_LIMIT` |
| `activepieces_sandbox_heap_limit_bytes` | `worker_id`, `host`, `box_id` | V8 heap limit enforced in the sandbox, as reported by V8. The sandbox is killed when heap used reaches it |
| `activepieces_sandbox_external_memory_bytes` | `worker_id`, `host`, `box_id` | Memory held outside the V8 heap by JS objects, mostly `Buffer` data. Not capped by `AP_SANDBOX_MEMORY_LIMIT` |
| `activepieces_sandbox_busy` | `worker_id`, `host`, `box_id` | `1` while the sandbox runs a job, `0` when idle |
| `activepieces_sandbox_piece_memory_usage_bytes` | `worker_id`, `host`, `box_id`, `piece`, `version` | Estimated live JS heap held by each piece loaded in the sandbox |
| `activepieces_sandbox_memory_limit_bytes` | `worker_id`, `host` | Configured `AP_SANDBOX_MEMORY_LIMIT`. Caps the V8 heap only |

```
# HELP activepieces_sandbox_memory_usage_bytes Total resident memory of the sandbox process and its children: V8 heap plus buffers, native memory and the Node runtime. This is what counts against the container memory limit
# TYPE activepieces_sandbox_memory_usage_bytes gauge
activepieces_sandbox_memory_usage_bytes{worker_id="aB3dE",host="worker-7",box_id="1"} 412516352
```

`box_id` is the stable slot number on the worker (1 to `AP_WORKER_CONCURRENCY`), so the series survive sandbox restarts.

### Total memory vs heap

A sandbox has two memory numbers, and they answer different questions:

| Question | Metric | Compare with |
| --- | --- | --- |
| Will the sandbox die at its heap limit? | `activepieces_sandbox_heap_used_bytes` | `activepieces_sandbox_heap_limit_bytes` |
| Will the kernel kill the worker container? | `activepieces_sandbox_memory_usage_bytes`, summed per worker | the container memory limit |

- **Total memory** is always larger than heap used. The gap is the Node runtime, `Buffer` data (see `activepieces_sandbox_external_memory_bytes`), native allocations, and any child process of a code step.
- **Heap used** includes garbage that V8 has not collected yet, so it can drop sharply after a collection.
- Do not divide total memory by the heap limit: total memory can exceed the heap limit while the heap still has room.

Alert before a sandbox runs out of heap:

```
activepieces_sandbox_heap_used_bytes / activepieces_sandbox_heap_limit_bytes > 0.8
```

The three heap metrics come from the sandbox itself. A sandbox that is busy in synchronous code may not answer in time, and those series skip that sample.

The per-piece number comes from V8's sampling heap profiler. It is an estimate and covers the JS heap only, not `Buffer` data or native addons.

<Note>
The worker samples sandbox memory every 15 seconds, and a sandbox only appears while its process is alive. When sandboxes are not reused between runs, a short run can start and finish between two samples.
</Note>
