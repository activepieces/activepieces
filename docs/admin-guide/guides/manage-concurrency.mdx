## Overview

Concurrency limits control how many flow runs can execute simultaneously within a project. When a project reaches its limit, new runs are queued and retried automatically with exponential backoff until a slot becomes available. Only published runs count; test runs from the builder are not limited.

<Note>
On a self-hosted instance, the limits apply only when `AP_PROJECT_RATE_LIMITER_ENABLED` is `true`. The default is `false`, and the limit field stays disabled or hidden until you set it.
</Note>

This is useful to:

- Prevent a single project from consuming all available workers.
- Protect downstream APIs from being overwhelmed by too many parallel requests.
- Ensure fair resource distribution across projects on your platform.

## Setting a Per-Project Limit

Only a platform admin can set the limit.

1. Navigate to **Project Settings > General**.
2. Find the **Max Concurrent Jobs** field.
3. Enter the desired limit, or leave it empty to use the platform default.
4. Click **Save**.

![Project Settings — Max Concurrent Jobs](/resources/screenshots/manage-concurrency.png)

If your plan includes worker groups, the field is not in Project Settings. Set the limit in **Platform Admin > Workers > Worker groups** instead: click the **Concurrency limit** of the project. A flow that has its own worker group is not limited by the project limit.

When the field is empty, the project uses the default limit. On Cloud, the default comes from your platform plan, and a project limit cannot go above it. On a self-hosted instance, the default is `AP_DEFAULT_CONCURRENT_JOBS_LIMIT` (`5` unless you change it). With worker groups, the default is also capped by the capacity of the worker group that runs the project.

## What Happens When the Limit Is Reached

When a project hits its concurrency limit:

1. New flow runs are **not dropped** — they are queued.
2. The system retries queued runs with **exponential backoff**.
3. Once an active run finishes and a slot opens, the next queued run starts.

This means flows will always eventually execute, but they may experience delays when the project is at capacity.

## Programmatic Management via Embedding

If you are embedding Activepieces, you can manage concurrency limits programmatically through the JWT token used to provision users. This allows you to group multiple projects into a shared **concurrency pool** so they share the same limit.

See [Provision Users](/embedding/provision-users) for the `concurrencyPoolKey` and `concurrencyPoolLimit` JWT claims.
