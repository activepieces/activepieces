# Flow Runs

A Flow Run records one execution of a specific flow version, from trigger to terminal state. It stores compressed step-by-step logs, supports pause/resume for delay and webhook waits, offers retry strategies, and emits WebSocket + application events for real-time UI.

### Entities & services
- **FlowRun** — id, projectId, flowId, flowVersionId, environment (PRODUCTION/TESTING), status, logsFileId, parentRunId (subflows), failedStep (JSONB `{name, displayName, message?}`), timeline (JSONB), archivedAt (soft delete).
- **12 statuses**: 3 non-terminal (QUEUED, RUNNING, PAUSED) + 9 terminal (SUCCEEDED, FAILED, TIMEOUT, CANCELED, QUOTA_EXCEEDED, MEMORY_LIMIT_EXCEEDED, INTERNAL_ERROR, LOG_SIZE_EXCEEDED).
- **Waitpoint** — row per paused step: `type` (DELAY|WEBHOOK), `version` (V0|V1), `status` (PENDING|COMPLETED), unique on `(flow_run_id, step_name)`. Fan-in barriers add `is_fan_in` (bool), `expected_children` (int, null until sealed) and `failed_to_dispatch` (int). A partial index on `resume_date_time` (`WHERE status = 'PENDING' AND resume_date_time IS NOT NULL`) serves the deadline sweep — every other read path leads with `flow_run_id` or the primary key.
- **LogsFile** — zstd-compressed File (type FLOW_RUN_LOG) holding the full executor context.

### How it works
- **Endpoints**: `GET /` (cursor paginated by composite `(created DESC, id DESC)`, filters incl. `failedStepMessage` ILIKE), `GET /:id`, `POST /:id/retry`, `POST /retry|cancel|archive` (bulk), waitpoint resume routes.
- **Retry strategies**: `FROM_FAILED_STEP` (rebuild context from logs, re-run from failure, prior outputs kept) or `ON_LATEST_VERSION` (fresh run on current published version). Both resolve the trigger payload via `resolveStepOutput`. If the trigger itself failed, they switch to `executeTrigger: true` to reprocess the raw event.
- **Pause/resume (V1 waitpoints)**: pieces call `createWaitpoint` + `waitForWaitpoint`. DELAY upserts a `RESUME_DELAY_WAITPOINT` BullMQ job; WEBHOOK resumes on an HTTP call to `/:id/waitpoints/:waitpointId[/sync]`.
- **Barrier** (`PauseType.BARRIER`): "pause this run until N things report back", as one mechanism. A barrier is a waitpoint carrying `sealed` + a nullable `policy` jsonb, plus one pre-created `waitpoint_signal` row per awaited thing (`id` doubling as the resume-link token, `refId` = the child run or approval link it stands for, nullable `sequence` = the producer ordinal, nullable `label` = the human name, small `result` jsonb). Release is an unconditional floor rule — **a sealed barrier releases once no signal is still PENDING** — so no configuration can hang it; `policy.requiredSuccesses` (K-of-N) and `policy.releaseOnFirstFailure` (veto) only ever release sooner. The test is `EXISTS`, not `COUNT(*)`; counts are taken once, at release, to build the `{total, succeeded, failed, rejected, canceled, notDispatched, stillRunning, timedOut}` summary (plus an inline `signals` array when `total <= 100`, else `signalsTruncated`). Evaluation is a coalesced `EVALUATE_BARRIER` job on `QueueName.BARRIER_JOBS`, deduplicated on the barrier id; the handler's first statement is `removeDeduplicationKey` and every producer commits its signal row before enqueuing, or the last signal's evaluation is silently dropped. Signals are deleted on release, in the same transaction that completes the waitpoint — summary, then complete, then delete. The deadline is set at **create** (`now + AP_PAUSED_FLOW_TIMEOUT_DAYS`) and nothing moves it. External resume is refused structurally: `resumeFromWaitpoint` rejects barriers by addressed type or, on the by-run legacy routes, by "does this run hold a PENDING barrier"; only the module-internal `releaseBarrier` may resume one. An external actor addresses a **signal**, never a waitpoint — `/v1/flow-runs/:id/signals/:signalId/confirm`. See decision 000015. Its one shipped caller is `PROCESS_IN_BATCHES`; what the next entry point inherits is on the [Fan-in entry points](./fan-in-entry-points.md) page.
- Logs backed up every 15s during execution for crash recovery; uploaded via 7-day JWT-signed URLs.
- **RUN_TELEMETRY job**: `flow-run-module.ts` registers a BullMQ system job (cron `50 23 * * *`, once daily at 23:50 UTC) that aggregates the day's run counts by `(projectId, flowId, environment)` in one transaction (5-minute statement timeout) and emits a `FLOW_RUN_CREATED` telemetry event per group. No-op when telemetry is disabled. The cron was `0/50 23 * * *` until GIT-1632, which also fired at 23:00 with partial counts.

### Gotchas
- **`MEMORY_LIMIT_EXCEEDED` is a per-sandbox heap ceiling, not a shared-infra symptom — and the trigger payload size says nothing about it.** `ErrorCode.SANDBOX_MEMORY_ISSUE` → `FlowRunStatus.MEMORY_LIMIT_EXCEEDED` (`worker/src/lib/execute/jobs/execute-flow.ts`), surfaced as *"Run failed due to exceeding the memory limit of {memoryLimit} MB"* from the `FLOW_RUN_MEMORY_LIMIT_KB` flag. `AP_SANDBOX_MEMORY_LIMIT` becomes `--max-old-space-size` on each forked engine child, so the figure is **peak heap of the whole run** — accumulated step outputs, loop iterations, large intermediates — not the payload. The classic report is "under 1 MB payload, fails at a *different* piece each time, some runs succeed": that randomness is the signature of a run sitting just under the ceiling, where whichever step allocates next tips it over. Triage the flow's memory profile, not the infra. **One exception before you rule out infra:** in the sandbox-*reuse* modes (`SANDBOX_CODE_ONLY`, `UNSANDBOXED`) the engine child is never reset between jobs, so a previous run's un-reclaimed heap does eat into yours — see the immortal-child gotcha in [workers](../execution-runtime/workers.md). In the process-per-job modes it cannot.
- **`resume-delay` system jobs are keyed per waitpoint** (`resume-delay-<waitpointId>`) and removed when the waitpoint is consumed. `upsertJob` silently no-ops on a duplicate jobId and cannot reschedule a one-time job, so a per-run id let a leftover fan-in timeout starve the next pause in that run of its backstop.
- **`upsertJob` does not no-op on a *failed* one-time job — it calls `existingJob.retry()`.** Only the pending/delayed case is a no-op. With `removeOnFail: { age: ONE_MONTH }` keeping the row, any caller that re-arms the same jobId on a schedule (i.e. a cron sweep) resurrects a permanently-failing job every single tick. That branch is right for the ~8 request-driven one-time callers (piece bundle, flow publish, AI provider, project delete…) and wrong for a cron backstop, so the default stays and **the sweep opts out on its own side**: it reads the job first and `continue`s on `isFailed()`. Check this branch in `system-job.ts` before building anything that re-arms through `upsertJob`. The attempt cap, the backoff and the dead-letter already exist one layer down — the system queue's `defaultJobOptions` sets `attempts: 2` + exponential backoff and retains failed jobs for a month, and the `failed` listener pages once attempts are exhausted; do not build a second counter in Postgres.
- **A retried run has its waitpoints cleared** — `FROM_FAILED_STEP` calls `deleteByFlowRunId`, so a re-executed step cannot inherit the previous attempt's waitpoint or barrier. `ON_LATEST_VERSION` copies `parentRunId` but must never copy `parentWaitpointId`: the barrier already counted the original child, so attributing the retry to it would inflate `terminal` and risk a premature release.
- **Waitpoint deadlines have two backstops, one per store.** The `resume-delay-<waitpointId>` BullMQ job is the Redis side; `WAITPOINT_DEADLINE_SWEEP` (system job, cron `* * * * *`) is the Postgres side. The sweep selects PENDING waitpoints whose `resumeDateTime` has passed on a still-PAUSED run and calls the same `scheduleTimeoutJob` the seal uses — `upsertJob` no-ops when the job is still there and BullMQ fires a non-positive delay immediately, so it is self-deduping and needs no change to `handleResumeDelayWaitpoint`. Three clauses in that one query are each load-bearing, and all three exist because a backstop must not be starvable by the failures it catches:
  - **`ORDER BY resumeDateTime DESC`, capped at 500 per tick.** Newest-first, deliberately not FIFO: a waitpoint whose resume permanently fails is by definition among the *oldest* rows, so under `ASC` 500 poison rows would mean no legitimate deadline is ever re-armed again. Under `DESC` the newest overdue deadline is always inside the batch whatever the poison count, and a genuine backlog still drains because served rows leave the set.
  - **A floor of `now - AP_PAUSED_FLOW_TIMEOUT_DAYS`.** Nothing in-tree expires a stale PAUSED run, so without a lower bound the first tick on any instance that ever lost Redis replays months-old runs at 500/min, many against deleted flow versions. A deadline overdue by more than the pause ceiling is not recoverable work. This is also what ages a poison row out of the sweep entirely.
  - **A dead-letter skip.** The sweep reads its own `resume-delay-<waitpointId>` job and `continue`s when it `isFailed()`, so an exhausted job is left dead-lettered instead of resurrected through `upsertJob`'s `retry()` branch every 60s. Note a skipped row still occupies one of the 500 fetched slots — do not assert an exact batch length in tests.
  - **`refill-paused-jobs.ts` is not a recovery path** — it is one-shot behind the Redis key `refill_paused_runs_v7` and filters `type !== PauseType.DELAY`, so it never saw barriers (created as `WEBHOOK`) and never runs twice. It is also the proof that losing the Redis alarm is *not* a fan-in-specific bug: it exists to re-arm lost **delay-piece** deadlines from `resumeDateTime`, i.e. the same repair the sweep now does permanently. Two further weaknesses it has and the sweep does not — `waitpointByRunId` keeps one waitpoint per run, so a run with several loses all but one arbitrarily, and its "already migrated" flag lives in the very store whose loss it repairs.
  - **The sweep's predicate names no `type` and no `version`,** so it covers every deadline-bearing waitpoint at once: delay-piece pauses, fan-in barriers, legacy V0 rows from `run.pause()` + `generateResumeUrl()`, and any registry piece passing `WEBHOOK` *with* a `resumeDateTime` (which got no job at all before it). It arrived with fan-in only because barriers time out on a deadline and nothing else, so a lost alarm hangs the parent every time, where a lost delay merely looks like a slow run. **Waitpoints with no `resumeDateTime` are outside its reach by construction** — approval, webhook-response and subflow-callback pauses wake only on an inbound HTTP call, which reads Postgres directly and so is immune to Redis loss anyway. Their gap is the opposite one (no timeout at all → hang to the pause ceiling) and needs a different fix.
- **The `flow_run.status = 'PAUSED'` predicate in the sweep is load-bearing.** `handleResumeDelayWaitpoint` returns early for a non-PAUSED run and `removeOnComplete: true` deletes the job, so without it a RUNNING row with a past deadline would churn a job every single minute forever.
- **`createForPause` only schedules a timeout job for `type === DELAY`.** A piece that passes a `resumeDateTime` with `type: 'WEBHOOK'` stored a deadline nothing acted on — the caller asked for a timeout and silently got none. Nothing in-tree does this, but registry pieces can; the deadline sweep is what now honours it (late by up to one tick rather than never).
- **A fan-in timeout leaves stragglers running.** The barrier releases with `stillRunning > 0` and nothing cancels those children. Each is bounded by `FLOW_TIMEOUT_SECONDS`, except descendants paused on their own waitpoints. Cancelling them is a new capability, not wiring: `getAllChildRuns` is recursive on `parentRunId` with `CANCELLABLE_STATUSES = [PAUSED, QUEUED]`, so it cannot stop a RUNNING child.
- **The cancel cascade *prunes* — it reaches a descendant only if that descendant's whole ancestor chain is also QUEUED or PAUSED.** `getAllChildRuns` applies `status = ANY(CANCELLABLE_STATUSES)` to the recursive CTE's **anchor** as well as its recursive term, and the recursive term can only join onto rows already in `descendants`. So a RUNNING child never enters the seed and its entire subtree is unreachable: a grandchild paused on an approval under a RUNNING subflow is never cancelled, and survives until `AP_PAUSED_FLOW_TIMEOUT_DAYS`. This is stronger than "cannot stop a RUNNING child" — it is "cannot see past one". Moving the filter to a final `SELECT * FROM descendants WHERE status = ANY($2)` fixes it in ~3 lines at the cost of walking every descendant row per cancel; deliberately not done yet because it changes shipped cancel behaviour for existing `EXECUTE_FLOW` subflow trees.
- **`flowRunService.cancel` resolves its targets through `filterFlowRunsAndApplyFilters`, not by raw id.** That filter also pins `environment = PRODUCTION`, so a TESTING run is never cancellable by id, and any predicate added there silently narrows what `POST /v1/flow-runs/cancel` can reach — the cascade in `getAllChildRuns` is separate raw SQL and does *not* inherit it.
- **`getByFlowRunId` prefers *any* COMPLETED waitpoint of the run, and both callers act on it by deleting it and enqueuing a resume.** (`resume-service`'s race-recovery branch and the runs-metadata worker's pre-completed check; `findNonFanInByFlowRunId` has the same shape for the fail-the-parent path.) Today that is safe only because `(flowRunId, stepName)` gives a run one waitpoint row per step and the PAUSED resume path deletes it. Any change that makes waitpoint identity *finer* — path-keying `stepName` so a loop-nested pause gets a row per iteration — turns those two reads into a **premature resume**: iteration N-1's COMPLETED leftover is picked while iteration N is still PENDING. Both call sites already hold the real waitpoint id, so `findByIdAndFlowRunId` is the fix; make it part of that change, not a follow-up.
- **A guard scoped to "the addressed waitpoint" cannot cover the legacy resume routes.** `/:id/requests/:requestId` and its `/sync` twin address no waitpoint id — they fall through to `legacyResume` / `legacySyncResume`, which pick the run's pending waitpoint *by run id*, which is why the barrier refusal there is `hasPendingBarrier({ flowRunId, projectId })` and not a type check. Four unscoped resume entry points, two shapes: any new "this kind of waitpoint may not be resumed from outside" rule needs both.
- **Retry refuses any run with a `dispatchIndex` — that column, not `parentWaitpointId`, is the "started mid-graph" discriminator.** Only `dispatchChild` writes it, and barrier attribution can legitimately be dropped (an unresolvable barrier dispatches the child anyway), so a child is recognisable by its dispatch index when it is not recognisable by its barrier. Retrying such a run is meaningless in both strategies: `FROM_FAILED_STEP` resumes from the trigger, so it would re-run the *parent's* whole prefix inside the child, and `ON_LATEST_VERSION` starts a fresh top-level run that no barrier is counting. `flowRunService.retry` throws `VALIDATION` before the retention check; the bulk path inherits it, which is why the child filter on `filterFlowRunsAndApplyFilters` is a second lock on the same door rather than the only one.
- **The two accepted fan-out limitations are surfaced as confirmations, not fixed.** Cancelling from the runs table now goes through `ConfirmationDeleteDialog`'s `warning` prop stating both halves of the pruned cascade — dispatched batches run to completion, *and* whatever they are waiting on is not reached either — and it needs no query to decide that. Retry-from-failed-step warns that already-succeeded batches re-run (repeated external writes, worker load and AI credits — never a re-bill; runs are not a billing unit), shown only for `FROM_FAILED_STEP` and only when the selection's flow version contains a `PROCESS_IN_BATCHES` step. That last check reads the *latest* version from the already-loaded flow list rather than each run's own `flowVersionId`: deliberately approximate, because the precise answer costs one version fetch per selected run for a warning.
- **`parentWaitpointId` (and any new run field) must be added to `RUNS_METADATA_UPSERT_KEYS`** in `runs-metadata-queue-factory.ts`. It is an allowlist — an unlisted key is silently dropped between the worker and the row with no error, the same failure class as forgetting `getEntities()`.
- **A new index on a mostly-NULL `flow_run` column must be partial.** Postgres indexes NULLs (unlike Oracle), and a non-HOT UPDATE inserts a tuple into *every* index on the table including ones on columns it did not touch — `flow_run` updates are essentially all non-HOT already (`status` sits in five composite indexes, `logsFileId` is indexed and the 15s log backup touches it). So a full index on a column that is NULL for ~every row adds permanent write amplification to the hottest write path in the product for reads that almost never happen. `WHERE <col> IS NOT NULL` makes that maintenance **zero**, not smaller, and the planner still uses the index for `col = $1` because `x = c` implies `x IS NOT NULL`. `idx_run_parent_waitpoint_id` is the worked example: partial, and widened to `(parentWaitpointId, projectId, status)` so the barrier's existence probe and release aggregate are index-only. `idx_run_parent_run_id`, `idx_run_logs_file_id` and `idx_run_triggered_by` are still full indexes on mostly-NULL columns.
- **Barrier children are unlisted, never invisible — and the discriminator is `parentWaitpointId IS NOT NULL`, nothing cheaper.** Children share the parent's flow id, flow version id *and* display name. Of the eight run list/count surfaces, five filter them out and three deliberately keep them: **user-facing and billing surfaces exclude children, ops and load surfaces keep them.** The five are `flowRunService.list` (one edit covering the runs endpoint, the builder's list, the agent tool and the MCP tool), `countByStatus`, `filterFlowRunsAndApplyFilters`, the billing usage report's daily-execution count and `platformAnalyticsReportService`'s `listRuns`. The three that keep counting are `healthMetricsService`, the telemetry daily rollup in `flow-run-module.ts` and the admin platform retry. Two of the five are correctness, not consistency: the shared filter-and-apply helper is the *only* thing stopping a filter-driven bulk retry from being a second door onto the refused mid-graph retry path, and the analytics filter multiplies a user-set per-trigger constant, so counting children makes a flow batching ten items claim eleven times the time saved. Reaching a child by id is the zero-work default (`getOnePopulatedOrThrow` already scopes by project) and `ListFlowRunsRequestQuery.parentWaitpointId` is the opt-back-in, ordered by `dispatchIndex` — a filter on the existing endpoint, not a new one. That listing also requires `dispatchIndex IS NOT NULL`, and the reason is the cursor, not taste: `Paginator` slices its composite cursor at the **first field missing from the decoded cursor object**, so a page ending on a NULL-index child encodes no `dispatchIndex`, emits *no* cursor predicate at all, and returns page 1 again forever. Any ordering added on a nullable column has this failure mode — either exclude the NULLs or do not sort on it. A child with no dispatch index is not a batch (only the webhook header path can make one) and stays reachable by id. `archivedAt` is a separate user-driven axis and is **not** reused for hiding.
- **Run detail resolves a step's output through one hook, and a batched body step is the reason.** Every surface that shows a step's run data — the data panel, the canvas status badge, the duration, the loop rail — used to call `flowRunUtils.extractStepOutput(name, loopsIndexes, run.steps)` itself. That lookup **cannot** resolve a step inside a Process in Batches body: the body ran in a *different run*, so its output is in another run's log file and no journal path reaches it. They now all go through `useStepOutputInRun` (`builder/run-details/use-batch-logs.ts`), which finds the enclosing batch step, resolves the selected batch to a child run id, and swaps in that run's `steps` — one seam, so a fifth caller cannot re-open the hole. React-query dedupes the per-node fetch, so every node in a body shares one request. The rail itself is presentational and shared with loops; keep batch-only behaviour (the 100-dot cap, the status vocabulary) in the batch wrapper, or a 5,000-iteration loop silently loses its dot grid too.
- **The UI's only route from a batch step to its children is `barrierId` in the step's own output.** The barrier lives on the `waitpoint` row with no read endpoint, and the released summary deliberately cannot enumerate its healthy children — so the executor writes `barrierId` (plus `totalItems`/`batchSize`) into both the paused output and the summary, and the builder reads it back to call `?parentWaitpointId=`. Querying by `parentRunId` instead looks cheaper and is wrong: two batch steps in one flow produce overlapping `dispatchIndex` values under the same parent. It does mean an internal id sits in a user-visible output JSON — the accepted price. Past the 100-dot grid, one batch resolves to its child through `?parentWaitpointId=&dispatchIndex=`, because the alternative is paging a 5,000-batch fan-out to reach batch 4,000.
- **The status-count query plans on `idx_run_project_id_environment_status_created_archived_at`, not the `created`-leading one — but only once the visibility map is healthy.** `EXPLAIN` it on a table whose VM is stale (right after a bulk `UPDATE`) and the planner refuses the index-only scan, falls back to a bitmap heap scan on `idx_run_project_id_environment_created_archived_at`, and you extend the wrong index. `VACUUM ANALYZE` first, then `EXPLAIN`. Appending `parentWaitpointId` as the trailing column keeps the scan index-only and pushes the child exclusion into the Index Cond instead of a post-heap Filter — measured on 1M rows / 50k per project: 42ms and 17.8k buffers → 5.5ms and 4k buffers, `Heap Fetches: 0`. A btree cannot be extended in place, so the migration creates the widened index under a new name **concurrently first** and only then drops the old one; dropping first would leave the hottest table in the product without that index for the length of a concurrent build. The children-listing query needs no new index — the partial `idx_run_parent_waitpoint_id` already covers it. **But the widened index only covers the status-count query, and the runs *list* was left behind.** `flowRunService.list` with no status filter orders by `created DESC` and plans on `idx_run_project_id_environment_created_archived_at`, which has no `parentWaitpointId` — so there the child exclusion is exactly the post-heap Filter this bullet says was eliminated, and every child row created since the newest visible parent is fetched and discarded before the page fills. Cost scales with children ever created, not with page size: right after a wide fan-out the first page walks the whole batch to return ten rows, and the table re-polls it every 15s while anything is non-terminal. **Resolved by making the three `created`-leading list indexes partial on `WHERE "parentWaitpointId" IS NULL`** — the only shape the list asks for, and it costs nothing to maintain (see the mostly-NULL bullet above): children are absent from the index entirely, so cost is proportional to page size instead of fan-out size, and a fan-out writes zero entries into them. Measured on 1.02M rows / 200 projects / a 20k-child fan-out as the newest activity: the no-filter list 4.5ms → 0.11ms, flow+status 6.2ms → 0.79ms, `countByStatus` 20.5ms → 1.2ms and the billing daily count 10.7ms → 2.3ms (both now `Index Only Scan`, `Heap Fetches: 0`). Trailing the column instead of a partial predicate was measured too and is the weaker fix — it moves the exclusion into the Index Cond but still walks every child's leaf pages, so it only bought 2-3x where partial buys 40x.
- **The status-leading run index must stay NON-partial, and that asymmetry is deliberate.** It is the only index left that can serve the ops aggregates in `healthMetricsService`, which by design count children (see the unlisted-children bullet) and therefore carry no `parentWaitpointId` predicate. Make all four partial and those seven aggregates fall to a `Parallel Seq Scan` on the whole table. The alternative — adding the predicate to `healthMetricsService` — was rejected because it silently reclassifies an ops surface as a user-facing one. So: `created`-leading and `flowId`-leading indexes are partial (list-only), the `status`-leading one is full and keeps `parentWaitpointId` as a trailing column so `countByStatus` stays index-only.
- **Benchmark run-list index changes against MANY projects, or the numbers lie.** With one project in a synthetic table, that project *is* half the table, so every project-scoped aggregate correctly picks a seq scan — which makes a partial index look load-bearing for queries that in production would happily use a full one, and makes `countByStatus` look broken when it is not. Seed ~200 projects so the target project is a low single-digit percentage of rows, and `VACUUM ANALYZE` before `EXPLAIN` (see the visibility-map trap above).
- **A run read must never widen its `flow_version` join, and the paginator is why it costs double.** `queryBuilderForFlowRun` is the single builder behind `list`, `getOne`, `getOnePopulatedOrThrow` *and* `findFlowRunOrThrow`, and the only thing any caller ever reads off the relation is `displayName` — the runs table column and the failed-step dialog. It used to be `leftJoinAndSelect`, which selects all thirteen `flow_version` columns including three `jsonb` ones: `trigger` (the whole flow graph, routinely TOASTed), `backupFiles`, `notes`. The `.addSelect(['"flowVersion"."displayName"'])` sitting beside it was raw SQL, so TypeORM mapped it to nothing — a duplicate column in the SELECT list that read as intent and did no work. Three things compounded it: `Paginator.paginate` uses `getRawAndEntities()` and `mergeAdditionalColumns` copies **every raw key not prefixed `<rootAlias>_` or `ap_cursor_`** onto the entity, so each row carried the graph twice (nested `flowVersion.trigger` *and* flattened `flowVersion_trigger`) — that flattening applies to any paginated list with a join, not just runs; `convertDatesToStrings` in `server.ts` then deep-walks both copies before zod strips them, so the wire payload stayed clean while the DB read, the heap and the per-request CPU did not; and `releaseBarrierWithoutLock` calls `findFlowRunOrThrow` up to 3× per barrier release just to read `status`. The fix is `leftJoin` + `addSelect(['flowVersion.id', 'flowVersion.displayName'])`, and **the PK is load-bearing, not decoration** — `RawSqlResultsToEntityTransformer.group()` keys joined rows by the alias's primary columns, so a partial relation select without the id silently fails to hydrate. Use entity-property notation (`'flowVersion.displayName'`); the quoted raw form is not mapped back onto the relation. Pinned by `list-flow-runs.test.ts`, which asserts on the **service** result, not the HTTP response — zod strips the heavy keys at serialization, so an HTTP-only assertion passes against the wide query too and proves nothing. Measured on 1M runs / 200 projects / 10k flow versions with a ~6.4 KB-on-disk TOASTed trigger, fully warm: a 50-row page went **1.59 MB → 15 KB** returned and 4.63ms → 0.56ms median, and the single-row read behind `findFlowRunOrThrow` 0.63ms → 0.30ms. **`EXPLAIN (ANALYZE, BUFFERS)` cannot measure this and will tell you there is nothing to fix** — it discards output rows, so it never detoasts the wide columns; the before/after execution-buffer difference was 9 pages and the only four-figure number in the plan was *planning* buffers. Time the query with its rows actually materialized (`\timing` + `\o /dev/null`). Two further traps in seeding it: give each project its own flow versions, or a page's lookups collapse into a handful of `Memoize` hits and the join looks free, and fill `trigger` with random text rather than repeated characters, or pglz compresses the payload away.
- **Never pair `DROP INDEX IF EXISTS "x"` with `CREATE INDEX CONCURRENTLY IF NOT EXISTS "x"` on the same name.** It opens a window with no index on the hottest table in the product for the length of the build, and it destroys an index pre-created out of band — which is the standard way to keep a large-table build off the boot path, since migrations run under a lock in `main.ts` *before* the app serves (the redlock auto-extends, so a long build delays the rollout rather than being preempted). Replace an index by building the new shape under a **new name first, then dropping the old name** — `1824000000000-AddBarrierAndSignals` does all five creates before all five drops. Residual risk to know about, deliberately not coded around: an aborted concurrent build leaves an **INVALID** index that a re-run's `IF NOT EXISTS` silently adopts, so after any migration that builds indexes check `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid`.
- **The barrier's release predicate is evaluated on every child's terminal transition, so the cheap half must be asked first.** `maybeResumeFanInBarrier` returns early on an unsealed barrier (zero queries) and then on a `LIMIT 1` non-terminal-child existence probe, before the `GROUP BY status` aggregate. Without that, N children × N rows is N² row reads per barrier. The probe's status list is derived from `isFlowRunStateTerminal` rather than hardcoded so it cannot drift when a status is added. It is *almost* always true for transitions 1…N−1 — a child whose row has not landed yet is neither terminal nor non-terminal, so while rows are still materialising some transitions legitimately pay the aggregate. Do not write a test asserting exactly one aggregate per barrier.
- **A BullMQ redelivery of a BEGIN job is a full non-idempotent replay from the trigger — persisted progress is never restored, it is destroyed.** `executionType` is immutable across attempts (`execute-flow.ts` derives the operation purely from `data.executionType`; job-data migrations only bump `schemaVersion`), and `fetchExecutionStateFromLogs` is reached exclusively on the RESUME branch of `resolveExecuteFlowOperation` — so attempt #2 of a crashed BEGIN starts from `FlowExecutorContext.empty()`, seeds only the trigger, and re-executes every prior step with its real side effects and freshly recomputed outputs. The replay also reuses the same `logsFileId`, so the first progress backup *overwrites* the crashed attempt's state file — no forensic record survives. `attemptsMade` is forwarded as `attempsStarted` but read by nothing; there is no idempotency guard on job start. Redelivery is bounded (`attempts: 2` + backoff, `maxStalledCount: 3`), after which the run is left as the OOM-kill bullet below describes. Consequence for anything resume-shaped: "re-enter with restored outputs" only exists on the explicit RESUME path — a crash re-entry re-resolves everything, so a step's input can legitimately differ between attempts even when no formula function is non-deterministic (any non-idempotent upstream step suffices).
- **A worker OOM-kill leaves the run stuck in RUNNING forever, and Cancel is greyed out.** The flow timeout is enforced *inside* the worker, so if the pod dies (OOM) nothing ever transitions the run to a terminal state; Cancel only applies to paused/queued runs, so the UI offers no way out and the run can't be retried either. Bug: activepieces#14372, fix PR #14374. Manual unblock on the customer's Postgres: `UPDATE flow_run SET status = 'CANCELED', "finishTime" = NOW(), updated = NOW() WHERE id = '<run id>' AND status = 'RUNNING';` (run id = last path segment of the run URL), then "Retry on latest version" replays the original payload.
- **Resume Confirmation Page (scanner guard)**: the `/confirm` route serves an HTML Approve/Disapprove page on `GET`/`HEAD` (never consumes) and only resumes on `POST` — stops email security scanners (Safe Links, Mimecast, Proofpoint) prefetching approval links. The deprecated bare `GET /:id/waitpoints/:waitpointId` still resumes for old emails. Slack is unchanged (server-side POST from webhook).
- **Cross-project isolation (subflow parent-fail)**: `markParentRunAsFailed` scopes its parent lookup to `{ id: parentRunId, projectId }` using the child run's authenticated `projectId`. `parentRunId`/`failParentOnFailure` arrive from spoofable webhook headers (`ap-parent-run-id`/`ap-fail-parent-on-failure`) on the public webhook endpoint, so without the scope a failed child in project A could complete a paused parent's waitpoint and resume it in project B. A cross-project parent id now matches nothing and the fail is a no-op; legitimate subflows are always same-project (Call Flow only targets flows in the caller's project).
- **There are four external resume paths, not three — the legacy V0 ones bypass every waitpoint guard.** `/:id/requests/:requestId` looks up a *V0* pending waitpoint; barriers and all modern pauses are `V1`, so it finds nothing and falls through to the legacy handlers, which read no waitpoint at all — they check `status === PAUSED` and enqueue a resume. Both legacy routes are `securityAccess.unscoped(ALL_PRINCIPAL_TYPES)`. Any guard added to the `/waitpoints/:waitpointId` handlers (the barrier refusal is the current example) must be added to the legacy path too, or it is not enforced. **The two legacy routes do NOT converge on one function** — `/requests/:requestId` → `legacyResume`, `/requests/:requestId/sync` → `legacySyncResume`, so a guard has to be added to both (`waitpointService.hasPendingBarrier` is the shared lookup they call).
- **All four resume paths converge on two chokepoints, so a resume-time guard belongs there, not on the routes.** `waitpointService.handleResumeSignal` already resolves the waitpoint under a `pessimistic_write` lock, so a check on the loaded row costs zero extra queries and cannot race — that covers all three `/waitpoints/:waitpointId` handlers at once. The two legacy V0 routes are the only callers that reach `enqueueResume` with no `waitpoint`, so `isNil(waitpoint)` there is an exact discriminator for them. **Settled: the refusal lives on `resumeService.resumeFromWaitpoint`, and the module-internal `releaseBarrier` is the only path that may resume a barrier** — by addressed waitpoint `type`, or, on the by-run legacy paths, by `hasPendingBarrier`. There is no boolean to forget and no parameter to default wrong. The barrier's legitimate release is distinguishable at both points: it always `complete()`s the waitpoint before resuming, so an external resume is the one that finds it still PENDING.
- **ResumeReason** (`WAITPOINT`|`RETRY`) discriminates whether FAILED steps are restored on resume: waitpoint resumes preserve them, retry resumes drop them so the failed step re-executes.
- **`executionJournal.upsertStep` must stay immutable, and step retry is why.** `runWithExponentialBackoff` re-uses the *same* `executionState` for every attempt, so a failed attempt writing its `FAILED` output must not reach back into that state. While the journal still mutated the shared `steps` map (fixed in #14453), the write cleared the step's `PAUSED` status, the next attempt read `isPaused === false` and ran `BEGIN` instead of `RESUME`, armed a **new** waitpoint and paused again — a fresh engine run per resume means `attemptCount` restarts at 1, so `maxAttempts` is unreachable. For Call Flow with wait-for-response that re-invoked the subflow every 4-5s forever with the parent stuck `PAUSED` (GIT-1712, ≤0.86.3, same defect at the old `packages/shared/...` path in 0.85.5). Pinned by the retry-on-failure subflow case in `execute-flow-e2e.test.ts`.
- **Retrying a step that failed on a waitpoint resume is intentional, not an oversight.** Attempts 2-4 re-run the RESUME branch against the same stored resume payload, which is pointless for a piece that just rethrows (Call Flow burns ~28s of backoff before failing) but is exactly right for one that does real work on resume — AssemblyAI's `transcribe` fetches the transcript in its RESUME branch, so a transient API failure there is worth retrying. Suppressing retry for resumed steps would trade that away.
- **Failed-trigger payload** survives past BullMQ job completion only because `buildFailedTriggerContext` writes it into the trigger step's `output` slot.
- **The trigger step's status IS the raw-vs-extracted discriminator for retry** — there is no separate field (a `payload` field was tried and removed as redundant). `FAILED` means "`output` holds a raw event, re-run `run()` on it" (`executeTrigger: true`); `SUCCEEDED` means "`output` is already the trigger's result, replay as-is" (`executeTrigger: false`). So any code that *fabricates* a trigger step without the engine having run — the `QUOTA_EXCEEDED` admission gate is the first — must pick the status from where its payload came: raw for sync webhooks, extracted for anything sourced from the worker RPC `submitPayloads` (which passes post-`TriggerHookType.RUN` output). Get it wrong on a polling trigger and retry re-polls against an already-advanced `lastPoll` cursor, so the run gets `undefined` or an unrelated newer item *and* silently consumes those fresh items' own runs.
- **Big step outputs**: over 32 KB inline → stored as a `LogSliceRef` pointer to a `FLOW_RUN_LOG_SLICE` file (`outputType === SLICE`); missing backing file throws `ENTITY_NOT_FOUND` (loud retry failure). Step *inputs* over 2 KB (`AP_FLOW_RUN_LOG_INPUT_TRUNCATE_THRESHOLD_KB`) become a display-only truncation placeholder.
- Retries only allowed on terminal states within `EXECUTION_DATA_RETENTION_DAYS`.
- **Credit metering (Autumn)**: on terminal runs (paid editions), `onFinish` does two tryCatch-wrapped billing steps that never break run completion. (1) A PRODUCTION run not in `QUOTA_EXCEEDED` charges +1 apCredit via `billingProvider.trackCredits` with idempotency key `{runId}:run`. (2) `flowRunAiUsageTracker` pre-scans the flow version for `@activepieces/piece-ai` steps, extracts per-provider/model usage from step outputs (`flow-run-ai-usage-extractor` — recurses into loops, fetches `FLOW_RUN_LOG_SLICE` files, falls back to flow-version settings on `**REDACTED**` models), meters `Σ(messages × model credit weight) + toolCalls` to Autumn (`{runId}:ai`, plus `{runId}:appSumoAi` for the managed-ACTIVEPIECES AppSumo cap), then emits the `AI_USAGE_PER_RUN` PostHog event — the license key is only the PostHog distinctId, no longer a gate on metering.
- **Every path that creates a *terminal* run must carry `parentWaitpointId`, not just the paths that execute one.** The barrier releases from a `GROUP BY` over `flow_run.parentWaitpointId`, so a child row that lands terminal without it is invisible: `terminal >= expected` never holds and the parent hangs to the barrier's `timeoutAt`. The `QUOTA_EXCEEDED` admission gate is the trap — `createQuotaExceededRun` writes a finished row straight to `runsMetadataQueue`, bypassing `flowRunService.start`, so it needs the field threaded explicitly at all three call sites (worker RPC `submitPayloads`, sync webhook, manual trigger). Found while merging the gate into the fan-in branch: neither side was wrong alone. Any future admit-without-executing path inherits the same obligation.
- **Credit gate is fail-open at admission**: the worker RPC `submitPayloads` checks `shouldBlockOnCredits` (blocks only when the platform is `billingEnforced` AND the cached balance is exhausted; CE default and Autumn-outage behavior is false). A blocked run is still admitted — as a `QUOTA_EXCEEDED` run with the trigger payload persisted in its log — so it stays retryable once credits return instead of being dropped. **`AP_EDITION=ee` skips the gate entirely** (`shouldBlockRunOnCredits` returns `false` before any provider call) so self-hosters pay no Redis/Autumn latency on admission — a temporary measure, see decision 000020.
- **Post-run metering window**: AI usage is metered only at `onFinish`, so a long run can spend past the credit limit before anything lands; interim by design — see decision 000016.
- **A resume must inherit the stream mode its BEGIN job used, or the builder freezes at the pause.** `streamStepProgress` decides whether the engine pushes per-step `UPDATE_RUN_PROGRESS` over the websocket (`EngineConstants.isTestFlow` is literally `streamStepProgress === WEBSOCKET`). `startManualTrigger` creates a **PRODUCTION** run with `WEBSOCKET`, but `enqueueResume` used to re-derive the mode from the environment (`TESTING ? WEBSOCKET : NONE`) — so the first leg streamed and the resumed leg went silent. The builder then kept its last-seen steps forever while the header still flipped to "Run Succeeded", because `flowRunHooks.onFinish` emits a bare `flow_run` row with no `step` and `test-flow-widget`'s `onUpdateRun` falls back to `previousSteps`. A `PROCESS_IN_BATCHES` parent makes it unmissable (always pauses, step stuck on `Paused`), but every manual-trigger run that pauses — delay, approval — had it. **"Streamed to builder" is the canonical name for this property**, and every site that decides it now routes through `streamStepProgressUtils` (`flow-run/stream-step-progress.ts`): both retry strategies, `test`, `startManualTrigger`, `enqueueResume`, and `flowRunHooks.onFinish`. They must agree — some decide what gets *sent*, one decides what gets *emitted*. `dispatchChild`, the webhook path and the worker pollers stay hardcoded `NONE`; they are never watched in a builder, and routing them through the predicate would buy a `flow_version` read for nothing. The resume leg reconstructs the mode from the trigger, so `startManualTrigger` now **rejects a non-manual trigger** — without that guard a hand-crafted `MANUAL_TRIGGER_RUN_STARTED` socket event streams on BEGIN and cannot be reconstructed on RESUME, which is the original bug again. Beware three names for one idea: the job field `streamStepProgress`, the engine getter `EngineConstants.isTestFlow` (now false advertising — PRODUCTION manual runs set it), and the predicate. Also note `DelayPauseMetadata.streamStepProgress` / `WebhookPauseMetadata.streamStepProgress` are declared in the schema but **never written or read**, and `flow_run.pauseMetadata` is a legacy `unknown` column no live code touches — neither is a usable carrier, so do not reach for them.
- **`failedStep` rides the *list* response, `steps` does not.** `queryBuilderForFlowRun` selects whole rows, so every row `GET /v1/flow-runs` returns already carries `failedStep {name, displayName, message}` — its `message` truncated server-side to `FAILED_STEP_MESSAGE_MAX_LENGTH` (700) by `truncateFailedStepMessage`. Any UI that needs "which step failed and why" can render it straight off the list row with **no `getPopulated` fetch**; `steps` is not a column at all (it is rehydrated from the logs file) so only the detail endpoint has it. Worth knowing before designing a per-run summary — the failure line is free, the step timeline is not.
  **Per-*run* duration is free the same way and for the same reason** (`finishTime - startTime`, both plain
  columns; `runs-table/columns.tsx` and the batch browser's row lane compute it identically off a list row).
  A per-*step* wall clock is the one that is genuinely impossible, and the two get conflated: `StepOutput`
  carries `duration` and no timestamps at all, so "10:00:04 — Send to CRM" could only ever be a cumulative
  sum of durations from the run's `startTime`, which is wrong the moment a step retries, the run pauses, or
  it resumes on a second leg. Say "no per-step clock", never "no duration" — the second is false and costs a
  reviewer a round trip.
- **The run page's only live-update mechanism is polling, not the websocket.** `useListenToExistingRun` (`flow-canvas/hooks.tsx`) refetches a non-terminal run every 5s while `location.pathname` contains `/runs`; the `UPDATE_RUN_PROGRESS` listener is registered only inside `flowRunsApi.testFlow()`, so it exists in the builder during a test and nowhere else. That poll was also gated on `RunEnvironment.PRODUCTION`, which left a TESTING run opened on `/runs/:runId` with no refresh path at all — reachable in one click, since batch children inherit the parent's environment and the batch-logs panel links straight to `/runs/<childRunId>`; the gate is gone. `BuilderStateProvider` is no help either — it seeds the zustand store once via `useRef`, so a changed `run` prop never reaches it and **every refresh must go through `setRun`**. `FlowRunPage` used to carry its own `refetchInterval: 15000` for that reason and it was pure dead weight; it is deleted. Two related traps in the same query: the `queryFn` must `return` the run (react-query v5 rejects `undefined` and parks the poll in a permanent error state), and the single `UPDATE_RUN_PROGRESS` listener is registered inside `flowRunsApi.subscribeToTestFlowOrManualRun` and was only ever removed when an event arrived with `finishTime` — navigating away mid-run left it firing `setRun` into an unmounted store, so `useTestFlowOrStartManualTrigger` now tears it down on unmount.
