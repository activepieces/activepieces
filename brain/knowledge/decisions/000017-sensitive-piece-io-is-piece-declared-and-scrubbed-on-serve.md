# Sensitive piece I/O is piece-declared and scrubbed on serve

## Decision

Piece authors declare sensitivity in the piece SDK: a new `sensitive: true` bit on `OutputSchemaField` (`packages/pieces/framework/src/lib/output-schema.ts`) for outputs, and an equivalent input-side marker (design deferred to the follow-up PR — see Consequences). The engine keeps writing the raw step output and step input to `flow_run.steps.<name>.{output,input}` as today, plus a computed `sensitiveOutputPaths: string[]` alongside the output, derived from the piece's declared schema against the real payload (array leaves get materialised per-index). The run-details API endpoint scrubs those paths to `**REDACTED**` before serving to the browser. The engine's variable resolver and piece `run()` invocation read the raw blob directly, so a downstream `{{steps.get_secret.SecretString}}` in the HTTP piece resolves to the real value; the resolver also consults upstream `sensitiveOutputPaths` while building `censoredInput`, so the downstream Input tab shows `**REDACTED**` for the referenced value without the piece losing access to the real one. Sample data (per-step, persisted on the flow version) stores the **raw output plus its `sensitiveOutputPaths`**, and the web app applies the scrub on load: sample data is consumed by the test-execution context to hydrate upstream step outputs during a single-step test run, so the raw copy is load-bearing at run time and cannot be dropped without breaking test steps that reference sensitive upstream values. Input values remain **plaintext at rest** on the flow version row (`settings.input.<propName>`), not encrypted; the guarantee is scoped to run-log visibility, not to at-rest confidentiality.

## Context

Customer opened a ticket because the `Get Secret Value` action in `@activepieces/piece-amazon-secrets-manager` returns `SecretString` as plain JSON, which then shows in the run-details panel when a downstream step (typically the HTTP piece) uses it in an Authorization header. Generalises to any piece whose action legitimately returns a token, key, or PII, and symmetrically to any piece prop that takes a sensitive value directly (an API key typed inline, a PII field configured on the step).

The platform-native answer is already Secret Managers references (`{{connectionId|path}}`, see [secret-managers.md](../wiki/connections-auth/secret-managers.md)), which resolve the value just-in-time and never enter step I/O. That path solves the same problem more strongly but is EE/Cloud only and needs the vault reference to fit the customer's shape. Customers on CE, or with a secret path the reference syntax cannot express, still need a piece-native answer.

## Why

- **Piece-author-declared, not a user toggle.** The customer opened the ticket because the default was unsafe. A "hide" toggle at flow-design time means the same ticket recurs every time a new customer forgets to flip it. `Get Secret Value` unambiguously produces a secret and an API-key prop unambiguously takes one; the piece author is the right decider and every user of the piece gets the safe default with zero config, matching `.claude/rules/self-hosting.md`.
- **Scrub on serve, keep raw where it was.** Downstream steps and piece `run()` invocations must see the real value. Storing the raw and filtering at the API boundary is symmetric across inputs and outputs, adds one bit to the piece schema, and reuses the existing JsonViewer without teaching it a second value shape.
- **Not deep-vault storage.** Moving raw values off the run row or off the flow-version row into a Redis-cached vault (mirroring the Secret Managers path) solves a strictly stronger threat (DB dump, run-export API, flow export) at the cost of a whole new resolution mechanism, when Secret Managers references already solve exactly that stronger case. Customers whose threat model needs the stronger guarantee should route through a reference, not through a piece I/O flag.
- **Not encrypt-at-rest for inputs.** The person who typed a sensitive input into a step already had flow-edit access, so they still see it in the step-config panel; the leak this decision closes is a *teammate viewing the run* seeing it in the run-log display. If a customer needs teammate-level isolation on the flow-version row, the right fix is role-based flow-edit permissions or a Secret Managers reference, not per-prop encryption inside the flow version.
- **Not automatic detection.** `redactSecrets` in `packages/web/src/app/builder/data-display/explanation-prompt.ts` already regex-matches keys like `authorization|token|api_key` for the AI-explain-error prompt, but that heuristic is unreliable as a general contract: misses fields (`SecretString`), false-positives on user data, and gives no way for a piece author to be explicit.
- **Sample data as raw + `sensitiveOutputPaths`, scrubbed on serve.** Sample data is not display-only — the test-execution context hydrates upstream step outputs from it when the user Test-Steps a downstream step, and that downstream step needs the real secret to make its outbound call. Storing `**REDACTED**` at rest would break Test Step for any flow that references a sensitive upstream field. So sample data stores the raw output plus its `sensitiveOutputPaths`, and the web app applies redaction on load — same wire shape as the run-details endpoint, one scrub layer conceptually.

## Consequences

Piece authors gain a new one-bit contract on `OutputSchemaField`. Existing pieces get zero change until they opt in; `Get Secret Value` and `Get A Random Password` in `@activepieces/piece-amazon-secrets-manager` gain `sensitive: true` on their secret-carrying output fields as the first adopters.

The **output side ships in this PR**. The symmetric **input side is deferred to a follow-up PR** (branch `feat/piece-declared-sensitive-input`), because the input-side type-system change (a new `Property.SecretText()` factory and `SECRET_TEXT_INPUT` `PropertyType`) touches every exhaustive `switch (property.type)` in the codebase and warrants independent review. The cross-step propagation shipped here means a downstream step whose input references a sensitive upstream output already gets `**REDACTED**` in its Input tab — the customer's primary leak (`Get Secret Value` → HTTP `Authorization: Bearer {{step.SecretString}}`) closes with the output PR alone. The remaining gap until the input PR is a user who **pastes a secret directly** into a piece prop (typing an API key into HTTP's Bearer field rather than referencing an upstream secret step).

The guarantee is **not visible in the UI run panel**, not **encrypted at rest**. On the output side the raw value still lives on `flow_run.steps.<name>.output` and on the flow version's stored sample data. A DB dump, a run-export API call, a flow export, or a platform admin with direct DB access still sees the real value. This is called out in customer-facing docs so the ceiling is honest, and Secret Managers references remain the recommendation whenever the customer's threat model reaches beyond casual over-the-shoulder viewing.

The output surface ships with one scrub layer at the run-details endpoint, one at the sample-data serve, one **`**REDACTED**`** sentinel (`SENSITIVE_VALUE_REDACTED` in `packages/core/execution/src/lib/engine/engine-constants.ts`), and one `sensitive: true` bit on the piece SDK.

## Gotchas

- **Do NOT redact `stepResponse.output` before emitting `TEST_STEP_FINISHED` / `TEST_STEP_PROGRESS` on the socket.** The client-side `SAVE_SAMPLE_DATA` operation persists whatever the socket delivers; server-side pre-emit redaction turns sample data at rest into `**REDACTED**`, which breaks Test-Step for every downstream step that references an upstream sensitive value (the exact ticket this decision was written to close). The scrub belongs in the browser (`applySensitivePaths` in the run panel + progress handler), not on the wire — `engine-run-callback-service.ts` must emit raw `stepResponse`, and `run-state.ts`'s `handleOnProgress` must apply `applySensitivePaths(response.output, response.sensitiveOutputPaths)` before `setSampleDataLocally`. PR #14611 initially added the server-side redact and re-broke the ticket; the fix reverts to main's raw-on-emit shape.
- **`SAVE_SAMPLE_DATA` with `sensitiveOutputPaths: undefined` must NOT wipe the stored paths.** Trigger-mock/poll/webhook-test paths on the web app call `updateSampleData({output: newPayload})` without carrying paths (they don't know the piece schema). Server-side `sample-data.service.saveSampleDataFileIdsInStep` must fall back to `existingPaths` when `params.sensitiveOutputPaths` is nil, or the second save silently exposes the trigger's sensitive fields on the data-selector.
- **`walkFields` in `output-sensitive-paths.ts` must special-case `dynamicKey` maps.** Without the branch, a schema like `{ key: 'accounts', dynamicKey: true, children: [{ key: 'accessToken', sensitive: true }] }` returns zero paths because the walker treats `children` as literal keys — so `readAt(nested, 'accessToken')` misses the real `acc_1`/`acc_2` map keys. Redaction silently no-ops on the whole subtree. Adding user-side controls (a "hide this step's output" toggle, a per-project "always redact these keys" policy) is deliberately deferred; if a real case shows up that a piece cannot decide for itself (the HTTP piece returning an arbitrary JSON where only the user knows which field is secret), that becomes its own decision on top of this one. Trigger outputs are covered by the same mechanism: `flow.operation.ts` collects `sensitiveOutputPaths` from the trigger's `outputSchema` against the resolved trigger payload and lands them on `flowRun.steps.<triggerName>.output` on both the success and USER-failed paths, so the redactor scrubs a trigger's leaves the same way it does an action's.
- **Persisted sample data's `sensitiveOutputPaths` goes stale across a piece upgrade.** A step tested under piece `0.1.0` (no `sensitive:true` fields) persists empty `sensitiveOutputPaths` alongside its sample output. If the user then bumps the step to `0.1.1`, which newly declares a `sensitive:true` field, without re-testing, `GET /sample-data` would serve the old raw value unredacted forever — the stored metadata reflects the version at save time, not the step's current version. Fixed by adding `sensitiveOutputPathsPieceVersion` to `SampleDataSetting` (captured at every OUTPUT save) and, on GET, only re-deriving paths live against the step's *current* piece schema when that stored version differs from the step's current `pieceVersion` — union'd with the stored paths, never replacing them. This keeps the common case (no upgrade since last test) at zero extra cost and confines the one live piece-metadata lookup to the actual upgrade-without-retest case. See `sensitive-output-paths-resolver.ts` and `piece-component-info.ts` under `packages/server/api/src/app/flows/step-run/`.
- **The redactor lives in `@activepieces/core-execution` (`step-output-redaction.ts`), not in the API.** The engine needs the *same recursive* walk (see the `sendUpdate` bullet below), and duplicating it is the mistake called out in the last bullet. `flow-run-service.ts` imports it via `@activepieces/shared`; the regression test moved to `packages/core/execution/test/flow-run/execution/step-output-redaction.test.ts`.
- **The `if (step.type === ROUTER) return redactLeafStep(step)` branch looks identical to the fallthrough and is NOT dead code — do not "simplify" it.** It splits the `StepOutput` union so TypeScript infers a single concrete `T` per call site. Collapsed into one call, `tsc` fails with `Type 'FlowActionType.CODE' is not assignable to type 'FlowActionType.ROUTER'`. A reviewer flagged it as dead, the removal was attempted, and the build caught it — the branch is load-bearing for inference, not for behaviour.
- **`step-output-redactor.ts`'s input is plain JSON, never a `GenericStepOutput` class instance — never call an instance method on it.** `flow-run-service.ts` builds `stateFile.executionState.steps` by `JSON.parse`-ing the run's log file; `JSON.parse` strips the prototype, so `step.setOutput(...)` throws `TypeError: step.setOutput is not a function` at runtime even though it type-checks fine (`StepOutput`'s declared type is the class, so TS trusts the annotation and can't see the prototype is gone). This regressed **three times** across this PR — landed with `.setOutput()`, fixed to plain-object reconstruction, then reverted back to `.setOutput()` by a later "cleanup" commit that re-broke it — because the type-checker gives zero signal either way. Rebuild the redacted step via `new GenericStepOutput({...step, output})`, never `step.setOutput(...)`; a `redactLeafStep<T, OUTPUT>(step: GenericStepOutput<T, OUTPUT>)` generic helper handles the union-of-class-types narrowing without `as` casts (plain object-literal spread alone fails a full `tsc` build against the class-typed `StepOutput` union — verify with an actual `npx turbo run build`, not just `lint`, before trusting this file again). Pinned by `packages/server/api/test/unit/app/flows/flow-run/step-output-redactor.test.ts`, which builds its inputs via `JSON.parse(JSON.stringify(GenericStepOutput.create(...)))` specifically to reproduce the prototype-less shape — don't "simplify" that helper away.
- **`context.output.update()` (the piece-authored progress-streaming API) must not pre-redact either — same gotcha as the first bullet, different code path.** `flow-run-progress-reporter.ts`'s `createOutputContext().update()` emits on the same `TEST_STEP_PROGRESS` socket event that `run-state.ts`'s `handleOnProgress` uses to persist sample data locally, so server-side redaction there bakes `**REDACTED**` into sample data at rest the same way emit-time redaction on `stepResponse` does. Fixed by adding `sensitiveOutputPaths` to `UpdateStepProgressRequest` (`@activepieces/core-execution`) and sending raw `data` + computed paths, mirroring the `uploadRunLog` path. No piece calls this API yet, so it was dormant, not user-visible — caught only by revalidating every finding against current code rather than trusting a written status table.
- **`collectSensitiveOutputPaths` lives once, in `@activepieces/core-execution`, not duplicated per-package.** It was briefly copy-pasted verbatim into both the engine and the API before landing here — don't repeat that. It can't take `OutputSchema` from `@activepieces/pieces-framework` directly (core-execution is forbidden from importing `pieces`, `.claude/rules/core-packages.md`), so it's typed against a local structural `SensitiveOutputSchema`/`SensitiveOutputField` duck-type (`key`, `sensitive?`, `dynamicKey?`, `children?`, `listItems?`) that any real `OutputSchema` satisfies structurally with zero import needed. `escapeSensitivePathSegment` lives beside it in `core-execution`'s `sensitive-path-utils.ts` (defined there, not re-exported from anywhere else) — moving it down to `@activepieces/core-utils` was considered so a `core-piece-types` walker could share it, but landed here once the walker itself moved to `core-execution`. **A "types" package is not a free dumping ground for algorithms just because the import direction happens to check out** — `core-piece-types`'s own charter is "the type and enum surface," and this walker was nearly landed there before being moved to `core-execution` (which already carries real behavior like `applySensitivePaths`/`GenericStepOutput`) — check a package's stated charter, not just its allowed-imports list, before adding to it.
- **`sendUpdate` in `flow-run-progress-reporter.ts` must use the recursive redactor, not a leaf-only one.** A LOOP step carries no `sensitiveOutputPaths` of its own, so a leaf-only redaction shipped `output.iterations[*].<inner>.output` raw over `UPDATE_RUN_PROGRESS`. In a test-flow the inner step's redacted update landed first and the loop step's raw update overwrote it in the run panel, with nothing refetching `GET /flow-runs/:id` afterwards.
- **A loop's `output.item` is a redaction surface of its own.** `loop-executor.ts` sets it from the raw `resolvedInput.items[i]`, so a loop over an upstream sensitive array showed `**REDACTED**` on the source step and the real secret on `loop.item` — and offered `{{loop_x.item.<leaf>}}` in the data selector. The loop step now compares resolved vs censored items and stamps `sensitiveOutputPaths: ['item']` when they differ; the value stays raw in execution state so inner steps still work.
- **Only stamp `sensitiveOutputPathsPieceVersion` when the caller actually computed paths.** Stamping it on *every* OUTPUT save meant a trigger-mock / webhook-test / poll save (five web call sites that never carry paths) wrote `paths: undefined` alongside `version: <current>`, which made `sensitiveOutputPathsResolver` short-circuit on version equality and serve the raw payload forever — no piece upgrade required. The decision lives in one pure, unit-tested helper (`sample-data-sensitivity.ts`) precisely because this line has been flipped twice.
- **`undefined` paths means "the caller does not know", `[]` means "computed, none".** The engine's `extractStepResponse` sends `?? []` so a re-test can *clear* stale paths after a piece drops `sensitive: true`; the web's trigger paths send `undefined` so the serve-side resolver re-derives instead. Collapsing the two back into one nil check reintroduces either the stale-redaction or the never-redacted bug.

## Deferred follow-ups

Logged here so they are not relitigated. None is reachable by the two current adopters (`Get Secret Value`, `Get A Random Password`).

- **`GET /v1/trigger-events` serves trigger payloads with no redaction** (`trigger-event-controller.ts`, `triggerEventService.list`/`saveEvent`). Pre-dates this feature, but it means the "trigger outputs are covered by the same mechanism" claim above holds for the run panel and sample data, not for the trigger-test panel. Needs the same `sensitiveOutputPathsResolver` + `applySensitivePaths` pass.
- **Test-Step hydration reads stored paths only** (`test-execution-context.ts`). The upgrade-without-retest re-derivation covers `GET /v1/sample-data` but not the engine hydration that feeds a downstream step's Input tab, so after a piece upgrade that tab can still render the real value.
- **`listItems` materialises one path per array element.** A 10k-row output produces a 10k-entry `sensitiveOutputPaths` array persisted into the run log and the `flow_version` JSON column, and `applySensitivePaths` copies the array once per path (O(n^2)). Wants a wildcard index segment or a single-traversal apply.
- **`collectTriggerSensitivePaths` runs `pieceRunner.describe` on every `ExecutionType.BEGIN`**, including the `!executeTrigger` passthrough where the trigger piece is otherwise never loaded. Cached per engine process, but it adds a piece load to the hot path of every webhook/polling run.
- **The dual log-slice upload is intentional and is NOT a storage leak.** Above-threshold sensitive outputs upload twice: `ref.fileId` points at the raw copy (engine and retry read it), `ref.url` at the redacted copy (what the browser downloads). The redacted copy's id is not referenced anywhere, which is a debugging inconvenience only — `fileService.deleteStaleBulk` (hourly, over `FLOW_RUN_LOG_SLICE`) sweeps by scanning the `file` table on `(type, created)` and deletes by primary key. It never traces `fileId` references out of `LogSliceRef` or run JSON, so both copies are identically-typed rows created in the same second and are collected on the same pass. Re-verified against current code; do not re-file this as an orphaned-file bug.
