# EE Authentication (SSO/RBAC)

Enterprise auth layer extending CE with SAML 2.0 SSO, Google/GitHub federated OAuth, OTP email flows, per-project RBAC, and managed-auth JWT exchange for embedding. All SSO paths delegate to `authenticationService.federatedAuthn()` which creates/links a user and issues a standard AP JWT.

### Entities & services
- `saml-authn/`, `federated-authn/`, `otp/`, `enterprise-local-authn/`, `project-role/` (RBAC), `ee-authorization.ts` (preHandler hooks), `managed-authn/`.
- `platform.federatedAuthProviders` stores `{ saml: {entityId, ssoUrl, certificate}, google: {clientId, clientSecret} }`.

### How it works
- **SAML SSO**: `POST /v1/authn/saml/login` returns IdP redirect; IdP POSTs assertion to ACS `POST /v1/authn/saml/acs`; service parses email/name → federatedAuthn → JWT. Gated by `platform.plan.ssoEnabled`.
- **Federated OAuth (Google/GitHub)**: `/v1/authn/federated/login` returns redirect URL; `/v1/authn/federated/claim` exchanges code → JWT. Redirects always use `FRONTEND_URL` (no custom domain).
- **OTP** (`EMAIL_VERIFICATION`, `PASSWORD_RESET`, `EMAIL_LOGIN`): per-type expiry (`OTP_EXPIRATION_MS` in `otp-service.ts`: 24h verification, 10-min reset, 10-min login); states PENDING/CONFIRMED; one row per `(identityId, type)`, DB-enforced. Resend re-delivers the existing pending value WITHOUT touching the row — expiry stays anchored to the value's creation, so resends cannot extend a (possibly compromised) OTP's lifetime; a new value is generated only once the old one is expired or spent (GIT-1733: the old early-return made resend a silent 204 no-op). The first two types carry a `randomUUID()` delivered as a link; `EMAIL_LOGIN` carries a 6-digit code the member types, and its row counts `attempts` so it dies after five wrong guesses — counted in raw SQL for the same reason resend leaves the row alone, since touching `updated` would buy the guesser another window. Known bounded edge: a resend requested just before expiry delivers a short-lived link; the next resend regenerates. See [000027](../decisions/000027-email-sign-in-is-a-typed-code-on-the-existing-otp-primitive.md).
- **Enterprise local auth**: `verifyEmail` (confirms OTP → sets verified), `resetPassword` (confirms OTP → updates hash), both audit-logged.
- **RBAC**: `assertPrincipalAccessToProject({principal, permission, projectId})` and `assertUserHasPermissionToFlow` (maps FlowOperationType → Permission). Authorization hooks: `platformMustHaveFeatureEnabled` (402 FEATURE_DISABLED), `projectMustBeTeamType`, `platformMustBeOwnedByCurrentUser`.

### Gotchas
- **Until the passwordless work, CE could not send an OTP at all, despite the entity being registered for every edition.** `otpModule` was registered only in the CLOUD and ENTERPRISE arms of `app.ts`, and `emailService.sendOtp` returned early when the edition was neither. So on CE the table existed, the migration ran, and nothing could ever be sent. `EMAIL_LOGIN` changed that: `otpModule` is now registered for COMMUNITY too, and `EMAIL_LOGIN` is the one type carved out of the paid-edition send gate, so the primitive reaches every edition. **The sign-in flow on top of it does not** — [000032](../decisions/000032-emailed-sign-in-codes-are-served-on-cloud-only-and-only-behind-a-captcha.md) put its three routes in a Cloud-only module that also needs a configured captcha, so the carve-out is currently unreachable and CE can still send nothing. The two link types are still paid-edition only. RBAC base types are CE; **SSO, managed auth, federated OAuth are EE/Cloud only**.
- **The public `POST /v1/otp` route deliberately cannot mint a login code.** Its `CreateOtpRequestBody` narrows `type` to `EMAIL_VERIFICATION | PASSWORD_RESET`, because that route is unauthenticated, carries no `rateLimit` config, and applies none of the sign-up guards. `EMAIL_LOGIN` is issued only through `POST /v1/authentication/otp/request`, which is rate limited and gated. Widening that enum back to the whole `OtpType` hands anyone an unthrottled "email a working sign-in code to this address" primitive.
- **A code sign-in must re-assert the platform's auth policy at verify time, not only at request time.** On Cloud `platformUtils.getPlatformIdForRequest` returns null for every unauthenticated request, so the request-scoped branch never runs there and the platform is only known after the identity is resolved. `verifyCode` therefore calls the same `assertEmailAuthIsEnabled` + `assertDomainIsAllowed` pair on the resolved preferred platform; without that, an email code signs a member into a platform that has deliberately disabled email auth or removed their domain. It is not asserted at request time on purpose, because reporting those errors for a resolved address would turn the request endpoint into an existence oracle.
- **`otpService.confirm` used to refresh its own resend lock.** `updated` is an `updateDate` column, so marking a row CONFIRMED touched it and the ten-minute guard then refused to issue that identity another code for ten minutes after a successful verify. Rows are deleted on confirm now.
- **One constant is both the expiry and the resend suppression.** `TEN_MINUTES` gates `confirm`'s freshness check and `createAndSend`'s "an OTP already exists" early return, so before this work a resend was impossible until the current credential expired, and the request endpoint still answered 204. Resend now re-delivers the existing value without touching `updated`.
- **`email-service.ts` is not exhaustive over `OtpType`.** `frontendPath` is a literal keyed by only two members but indexed by the whole union, so adding a member is a compile break; its sibling `otpToTemplate` is typed `Record<string, EmailTemplateData>`, which type-checks and hands `undefined` to the sender at runtime instead.
- **The SAML round-trip used to forget where the login was going, and the obvious fix moves a trust boundary.** Three losses, all in the redirect and none in the assertion handling: the web app called `/api/v1/authn/saml/login` with no `from` (`saml-login-form.tsx`, `third-party-logins.tsx`), `/authenticate` hardcoded `navigate('/flows')`, and `/acs` redirected to `networkUtils.getRequestBaseUrl(req)` — an origin with no path — so a subpath instance 404'd at `example.com/authenticate`. Password sign-in hid all three by never leaving the origin; they surfaced the moment a login *started* elsewhere, so MCP OAuth (`/mcp-authorize` → `/sign-in?from=…`) abandoned the authorize request. **The trap worth remembering:** it is tempting to carry the starting origin through the IdP in RelayState. Do not. `/acs` derives its redirect from the IdP's POST, whose `x-forwarded-host` only the operator's edge sets; capturing the origin at `/login` instead hands that decision to an endpoint an attacker can call directly, and `networkUtils.candidateHosts` deliberately *prefers* `x-forwarded-host` — so a spoofed header would mint a return target for `evil.com`, and a phished IdP link carrying it would deliver the victim's session token to `/authenticate?response=`. Signing or storing the captured origin does not close that; only resolving it against an allowlist would. **What shipped avoids the question entirely:** MCP consent is served from the frontend base (see [[mcp-server]]), so login leaves and returns to the same origin in the same tab. `from` rides `sessionStorage` (`lib/federated-login-redirect.ts`, saved by `useStartSamlLogin` at the three SAML entry points, consumed and cleared at `/authenticate`). It stores **only** `/mcp-authorize`, exactly or followed by `?` — every other destination, including legitimate in-app deep links, is refused and SSO lands on the default page as it always has. That narrowness is deliberate: the mechanism exists for the one flow that cannot survive losing its continuation, and scoping it by destination keeps deployments without MCP on their existing code path. Gating it on `AP_MCP_URL` instead would not work — `getMcpUrl` falls back to `AP_FRONTEND_URL`, so the `MCP_URL` flag is never null, and `/authenticate` consumes synchronously on mount while flags arrive async, and `/acs` builds its redirect from the request origin (`new URL('/authenticate', networkUtils.getRequestBaseUrl(req))`), which is the one place the SPA can route it. No RelayState, no Redis, no allowlist, and the origin never crosses the IdP.
- **Restoring the subpath on the SSO return *breaks* SAML sign-in on a prefixed instance, because the SPA cannot route a prefixed path — and the bare-origin version it replaced accidentally could.** Verified end to end against a real SimpleSAMLphp IdP behind Kong (`strip_path: true`) with `AP_FRONTEND_URL=http://host/activepieces`: the assertion validates and `/acs` redirects to `http://host/activepieces/authenticate?response=…` exactly as intended — and the SPA then bounces away with the session response unconsumed, because `createBrowserRouter` has no `basename` (see [[web-feature-anatomy]]). Measured both ways on one harness: `new URL('/authenticate', getRequestBaseUrl(req))` drops the path, lands at the origin root, and signs in; restoring the prefix kills the login. So the two kinds of URL AP emits have opposite requirements and **must not share a helper**: *protocol URLs the server advertises* (OAuth issuer and endpoints, ACS `Destination`, webhooks, invitation links) need the configured base, while *browser landing routes* (`/authenticate`, `/mcp-authorize`, `/sign-in`) must stay wherever the SPA can actually route, which today is the origin root. With the origin-root return and the UI at the root, the whole SSO-into-MCP chain completes in a browser — IdP credential form → `/acs` → `/authenticate` → `from` restored from `sessionStorage` → consent → code → token → `tools/list`; that chain is the point of the `from` round trip, and it is what a prefixed instance loses. Until the SPA gains `basename` + vite `base`, prefixing a browser landing route is always wrong.
- **AP accepts only *plaintext* SAML assertions, and an encrypting IdP fails with a misleading error.** `createSp` sets `isAssertionEncrypted: true`, but samlify reads that flag off the **remote** entity (`flow.js`: `decryptRequired = from.entitySetting.isAssertionEncrypted`), where `createIdp` sets `false` — so the SP-side flag is inert. It could not work anyway: samlify decrypts with `entitySetting.encPrivateKey`, which AP never sets (`privateKey` holds `samlProvider.idpCertificate`, used for signing). Point an IdP with `assertion.encryption` on at it and the failure surfaces as `ERR_UNMATCH_ISSUER` — not a decryption error — because the issuer comparison reads the *assertion's* issuer out of a decrypted document that does not exist. Configure IdPs to sign but not encrypt.
- The SSO settings page (titled **Authentication** since ENG-977, route still `/platform/sso`) is wrapped in `PlanFeatureSample feature="sso"`, which renders the real page faded under an upgrade card when `ssoEnabled` is off. It has no sample data, so a locked platform sees its own real values.
- **The allowed-domain list only runs once a platform is known, so on Cloud it misses most first sign-ins.** Self-hosted always knows the platform (the oldest one), so `assertDomainIsAllowed` runs in `signUp` for every provider and on every email-and-password and email-code sign-in; returning Google/SAML users skip it. On Cloud `getPlatformIdForRequest` is `null` for anyone not signed in, so `signUp` runs without a platform and skips the check, and `provisionUserInvitation` then makes the person a member of every invited platform without checking either. Net effect on Cloud: password and email-code sign-ins are checked once the person is a member, Google is never checked, SAML only when the person has no account anywhere, and an invited person outside the list joins and is then refused at their next password sign-in. Community never checks. Until ENG-999 fixes this, the Authentication page copy is split by edition: Enterprise says the list limits who can *join*, Cloud says only "email and password sign-in"; ENG-999 removes the split.
- **To reproduce "SAML connected + pending domain" locally, go through the API, since the UI cannot create it.** Verify a domain, save SAML (`POST /v1/platforms/:id` with `federatedAuthProviders.saml`; placeholder metadata is accepted), then `POST /v1/authn/saml/sso-domain` with a different domain: the new one is pending and SAML is kept. Switching discards the old domain's verification, so re-verifying it later needs a new TXT record.
- **"Verify DNS" asks the API host's own resolver, so a correct TXT record can still fail for a few minutes.** `txtRecordMatches` calls Node's `resolveTxt`, which uses the OS resolver (locally often Tailscale's `100.100.100.100`), not a public one; until that cache expires the old record set comes back. Compare `dig TXT _activepieces-verify.<domain> @8.8.8.8` with plain `dig` before suspecting code. Leftover `activepieces-verify=` records from earlier attempts are harmless: any matching record passes.
- **The SAML walkthrough keeps both steps mounted and hides the inactive one with a `hidden` class, so a test that finds step 2 text passes even when navigation is broken.** Assert on the step bar instead (`aria-current="step"`, `disabled`) and on `Next`/`Save` state. The SAML step opens only once the domain is verified, except when SAML is already connected (pre-domain setups), so those admins can still reach their connection and Disable.
- **Only removing a verified SSO domain deletes SAML; a pending one goes and SAML stays.** `updateSsoDomain(null)` deletes SAML only when the current verification is `VERIFIED`, so "Cancel verification" matches `expirePendingSsoDomains`, which clears `ssoDomain` and `ssoDomainVerification` after `PENDING_DOMAIN_TTL_HOURS` (3) without touching `federatedAuthProviders`. A platform reaches "SAML + pending domain" when it set up SAML before #13071 added domains (May 2026, no backfill) and only now verifies one, or by changing the domain (the pre-ENG-977 page's "Update domain", or the API; ENG-994); deleting SAML there would remove SSO that was working.
- **Removing the SSO domain also deletes SAML, in one update.** `updateSsoDomain` with `null` clears `ssoDomain`, `ssoDomainVerification` and `federatedAuthProviders.saml` in the same `platformService.update`; the page's Remove domain is that one request. Without a domain the sign-in page could not start SSO anyway (`/discover` needs a verified domain), and new SAML connections already require one. History: #13071 shipped a Remove button that never worked (see the next bullet); #13072 dropped the button without a stated reason; ENG-977 fixed the server and brought it back. **Changing** to a different domain still keeps SAML while the new one is pending. The sign-in page's SSO path is closed then (no verified domain for `/discover`), but IdP-initiated sign-in or a direct `/login?platformId=` link still works, and `assertEmailMatchesSsoDomain` skips unverified domains on purpose so platforms that had SAML before domain verification keep working; so the platform's own IdP can sign in any email until the new domain verifies (ENG-994). `verifySsoDomain` on an already-verified domain returns without re-checking DNS, so the page only offers "Verify DNS" while pending. Removal deletes SAML rather than keeping it saved because SAML has no on/off state: a kept config would stay live with no domain check. When ENG-982 adds on/off, removal should switch to turning SAML off (and the remove dialog and docs that say "deletes" change with it).
- **Every domain claim gets a fresh TXT value, so a record left at the DNS provider never re-verifies anything.** `computeNextVerification` issues `activepieces-verify=<new apId>` for any new or re-added domain, and `txtRecordMatches` needs that exact value at `_activepieces-verify.<domain>` (any of the TXT strings there may match, so admins can add the new value beside the old one). Removing and re-adding a domain therefore always lands on PENDING, and a stale record cannot verify the domain for this platform or another one.
- **`platformService.update` writes most fields with `spreadIfDefined`, which drops `null` as well as `undefined`, so those fields cannot be cleared through it.** That silently made "remove the SSO domain" a no-op while the endpoint still answered `{ ssoDomain: null }`. `ssoDomain` and `ssoDomainVerification` now use `spreadIfNotUndefined`, like `themeColors`; any other field that needs clearing must switch the same way, and a test that reads the row back is the only thing that catches it.
- Managed auth gated separately by `embeddingEnabled` (signing keys). See the Managed Auth page.
- The authn rate limiter (`core/security/rate-limit.ts`) is registered with `global: false` — it protects NOTHING by default. Every public endpoint that sends email or does auth work must opt in per-route via `config.rateLimit` (see `authentication.controller.ts` / `otp-controller.ts` for the `API_RATE_LIMIT_AUTHN_*` pattern).

### Key files
Entry point: `assertPrinicpalAccessToProject` (yes, misspelled in the source), exported from `project-role/rbac-service.ts` and called from `core/security/v2/authz/authorize.ts` on every project-scoped request.

- `packages/server/api/src/app/ee/authentication/` — EE auth module root: `saml-authn/`, `federated-authn/`, `otp/`, `enterprise-local-authn/`, `project-role/` (RBAC service + middleware), and `ee-authorization.ts` plan/ownership hooks
- `packages/server/api/src/app/core/security/v2/authz/` — where RBAC gets wired into request authorization
- `packages/server/api/src/app/ee/managed-authn/` — managed auth JWT exchange for the embedding SDK
- `packages/core/shared/src/lib/ee/authn/` — shared enterprise authn exports, ACL types, verify-email and reset-password DTOs
- `packages/core/shared/src/lib/ee/otp/` — OTP model schema and the `OtpType` enum
- `packages/web/src/features/authentication/` — sign-in form, third-party login buttons, verify email, reset password, auth hooks, managed auth client
- `packages/web/src/app/routes/platform/security/sso/` — SSO settings page, SAML dialog, allowed domains dialog
- `packages/web/src/app/routes/authenticate/` — SAML ACS callback landing page
