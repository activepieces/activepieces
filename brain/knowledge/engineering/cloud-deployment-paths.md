# Cloud Deployment Paths

How code reaches `cloud.activepieces.com`. `continuous-delivery-cloud.yml` is the **Cloud gate** (ENG-1021): `cut` → `e2e-matrix` + `upgrade-test` → `report` + `tickets` → `approve` → `deploy` (migration check, canary, fleet) → `linear-release`. It runs Sunday to Thursday at 08:00 UTC and by hand.

## The normal path
`cut` takes the newest `main` commit whose `e2e-staging` check run passed (a manual run can name a `sha`, which must also have passed), and stops a scheduled run when the fleet already runs it. Every later job uses the `version.sha.beta` image that staging built from that commit; nothing is built again. The `approve` job holds the only approval (`production` environment). The `deploy` job then runs the breaking-migration check and deploys the canary and the fleet, a few minutes apart.

## Hotfixes
A hotfix merges into `main` like any other change, and a manual run deploys it once `e2e-staging` passes. There is no path that builds from a branch. `emergency-cloud-deploy.yml` and `continuous-delivery-rollback.yml` stay outside the gate.

## Staging (upstream of the gate)
`continuous-delivery-stg.yml` builds every push to `main` and deploys it with **Kamal**, not Kubernetes: it SSHes to the devops box and runs `kamal deploy --config-file=config/{app,worker}.yml` from `/root/mrsk/stg`. App containers live on one host, workers on another; `kubectl`'s `stg` context on that box is dead and points at a node that no longer runs k3s — ignore it. Env vars for staging go in `config/app.yml` under `env.clear` (secrets are name-listed under `env.secret` and read from `.kamal/secrets`). After both deploys, `e2e-staging` runs the Playwright suite against staging; its check run on the commit is what the gate's `cut` reads.

## Gotchas
- **Kamal reads its config at deploy time, so editing `config/app.yml` during an in-flight CD run silently misses.** The build takes ~5 min and the deploy job reads the file when *it* starts; an edit that lands in between applies to neither the running containers nor the deploy. Worse, Kamal replaces containers one at a time, so a mid-deploy edit can leave app_1 and app_2 disagreeing about a flag — which reads downstream as a flaky feature, not a config race. Always re-run `kamal deploy --version <same tag> --config-file=config/app.yml --skip-push` after editing, and verify with `docker inspect <container> --format '{{range .Config.Env}}...'` on **every** container, not one. The command needs a TTY (`ssh -tt`); without it Kamal exits 0 having done nothing ("the input device is not a TTY").
- **The breaking-migration check runs in the `deploy` job, after the approval.** It fails when any pending migration carries `breaking = true` (rollback safety — see `tools/scripts/check-manifest-migrations.ts`), so the fleet never deploys. To ship a breaking migration on purpose, run the gate by hand with `skip_migration_check`.
- **The approval sits before the canary on purpose.** The canary runs migrations on the shared database at boot, so a canary deploy that waits days for the fleet's approval brings back the ENG-1062 problem.
- **A reusable workflow checks out `github.sha`, not the candidate.** `e2e-matrix.yml` and `upgrade-test.yml` take a `ref` input, and the gate passes the candidate SHA; without it the specs come from the newest `main`.
- **The canary and the fleet deploy in one job on purpose.** GitHub keeps only one pending job per concurrency group, even with `cancel-in-progress: false`, so with a lock per job a third run could replace the second run's pending fleet deploy after its canary had migrated the shared database. The `deploy` job's group is `promote-production`, the same as `continuous-delivery-rollback.yml`, so a rollback cannot interleave with a gate deploy either.
- **`/flags` cannot prove the upgrade test swapped images.** After the release sync PR, `main` carries the same `package.json` version as the last release, so the upgrade test compares the running containers' image ID with the candidate's instead. Its `swapped` output tells `report` whether a red result is the candidate or the setup before the upgrade.
- **The canary has no daily schedule and no manual dispatch since ENG-1062.** It shares the prod database and Redis, so a daily build of `main` ran newer migrations under the older fleet (2026-10-06: days of old-shape writes). The canary app runs migrations at boot, so it now gets only the image of a Cloud deploy (since ENG-1021 it has no workflow of its own), and `continuous-delivery-rollback-canary.yml` (which ran `down()` on the shared database) is deleted. The Cloud rollback workflow does not touch the canary hosts, so after a rollback they keep the bad image until the next Cloud deploy.
- **`docker pull … error from registry: denied` on the ops host can be transient.** Seen 2026-08-12 pulling a `.beta` tag to the canary host; re-running the same job with no other change pulled and deployed fine. The tag existed in GHCR the whole time. Re-run once before suspecting the host's registry credential — GHCR does answer `GET /v2/` for a token that cannot pull, so login-succeeds/pull-denied is *consistent* with an expired credential, but it is not evidence of one.
- **Never put a BuildKit cache mount on `/var/cache/apt` or `/var/lib/apt`.** The `node:*-bullseye-slim` base ships `/etc/apt/apt.conf.d/docker-clean`, which wipes downloaded `.deb`s and sets `Keep-Downloaded-Packages "false"` — so the mount caches nothing, but it does persist stale `apt` lists and `partial/` leftovers across Depot builds. When `bullseye-security` republishes and old `.deb`s rotate out, the next build dies on `Hash Sum mismatch` / `Unable to fetch some archives` → `exit code: 100`, which reads like a missing package but isn't. Removed from both Dockerfiles on 2026-08-12; a plain `apt-get update && apt-get install` is what works. Also: bullseye `main` has been frozen since Aug 2025 and Debian 11 LTS ends Aug 2026, so the base image needs a bookworm bump.
- **Building the image locally from a branch can fail before your code is even copied.** Two independent causes seen 2026-09-10 on arm64: (1) `snapshot.debian.org` served corrupt `.deb`s (`Hash Sum mismatch`, `File has unexpected size … Mirror sync in progress?`, `Bad header line`) across three retries, with no cache mount involved — workaround is a throwaway Dockerfile whose base stage is `FROM ghcr.io/activepieces/activepieces:<root package.json version> AS base` (same bun/npm/isolated-vm tooling, no apt), plus `ENV NODE_ENV=development` and `RUN rm -rf /usr/src/app` at the top of the build stage (the published image sets `NODE_ENV=production`, which makes `bun install` skip devDependencies). (2) `bun install --frozen-lockfile` fails whenever any workspace `package.json` version differs from its `bun.lock` entry; check with `bun install --lockfile-only` in a copy and `diff` the result before blaming your change.
- **`breaking = true` on a migration and the `⛓️‍💥 breaking-change` PR label are different axes.** The migration flag is about rollback safety and is what stops deploys; the label is about self-hoster upgrade impact and is enforced by `breaking-change-check.yml` on PRs. Neither implies the other.
- **The Dockerfile's prune step deletes `packages/pieces/core` (and every community piece but the api's 5), then re-runs `bun install` without a lockfile.** Any other kept workspace that declares one of the removed pieces as `workspace:*` breaks the image build with `Workspace dependency "@activepieces/piece-…" not found`. #15842 hit this by adding core pieces to the engine's devDependencies for CI tests; the prune step now strips the engine's `@activepieces/piece-*` devDependencies. Check any new piece dependency outside `packages/pieces` against that step.
