# Event Destinations

Streams platform/project activity events to webhook URLs in real time. Internal Activepieces flow webhooks are valid targets, so operators can route events into a flow and fan out to Slack/Gmail/Teams/HTTP without leaving the platform. EE/Cloud only, gated by `eventStreamingEnabled` on both the API (402 preHandler) and delivery (`eventDestinationHooks`). Lives in platform admin at `/platform/audit-log/streaming` (Event Streaming), with the setup page at `/new` and `/:id`.

### Entities & services
- **EventDestination**: one URL receiving a chosen subset of the `ApplicationEventName` events, at PLATFORM or PROJECT scope.
- **Scope**: PLATFORM (all platform events) or PROJECT (currently only `FLOW_RUN_FINISHED`).
- **Format**: how a destination encodes each event on the wire — `RAW` (the event JSON, the default and what every pre-format destination sends), `OTLP_JSON`, or `OTLP_PROTOBUF` (an OTLP/HTTP logs `ExportLogsServiceRequest`, built by `otlpLogs` in `@activepieces/server-utils` on top of evlog's `toOTLPLogRecord`).
- Delivery via BullMQ queue (`WorkerJobType.EVENT_DESTINATION`).

### How it works
- `eventDestinationService.trigger()` finds matching destinations and classifies each URL as internal vs external.
- **Internal** (URL origin == instance's public API origin, path under `/v1/webhooks/<flowId>`, any route suffix): dispatched directly via `webhookService.handleWebhook` — no outbound HTTP, so the SSRF filter never sees a self-referential private-IP call (GIT-1539). A `/draft` URL runs the latest version; a `/test` URL only saves sample data and does not run the flow.
- **External**: queued as ONE_TIME jobs, POSTed via `safeHttp.postForStatus` (SSRF-protected, reads only the status); delivery failures logged at error level.
- Endpoints: `POST/GET/DELETE /v1/event-destinations` (+ `POST /:id` and `PATCH /:id`), and `POST /test` sends a mock event (defaults to `FLOW_CREATED`, format `RAW`) built by `buildMockEvent()`.

### Gotchas
- **A header value is decrypted in exactly one function, `decryptBoundHeaders`, and only on the way out.** Two callers: `resolveDeliveryHeaders`, the method the worker calls over RPC just before an external POST, and the internal dispatch to a handler flow. The `headers` column stores the URL the values were saved for and a *per-key* map of ciphertexts (`{ url, values: { [name]: {iv,data} } }`), not one blob over the whole map, so the key names are readable without the key. That is what lets `maskHeaders` be pure and synchronous, lets `update()` keep a value by copying its ciphertext, and stops one unreadable row from 500-ing the whole list endpoint. `grep decryptString packages/server/api/src/app/event-destinations` should return one line. An `EVENT_DESTINATION` job carries the destination id, never the headers — copying `resolveAiProvider`, because the worker has no database and no `AP_ENCRYPTION_KEY`.
- **A stored header value is bound to the URL it was saved against, on write and on send.** `update()` answers 400 if the request changes `url` while carrying any stored value over (a `null` for a stored key, or an omitted `headers` field entirely — both branches, or it is bypassed by omission). Without that rule "write-only" is decorative: anyone who can edit a destination points it at their own endpoint and the next audit event delivers the secret for them. `update()` reads the row `FOR UPDATE` inside a transaction, so two overlapping edits cannot combine into a new URL with headers typed for the old one (and an omitted `format` is read fresh, so an events-only edit cannot undo a format switch — do not "fix" that by dropping `format` from the UPDATE, that reopens the webhook URL + `OTLP_PROTOBUF` pair). On send, the worker passes the job's `webhookUrl` to `resolveEventDestinationHeaders`, which matches on `url` too: a job queued before the URL changed (a retry, say) gets `null` and is dropped, instead of carrying the new secret to the old URL. The stored `url` makes the binding hold outside `update()` too: `decryptBoundHeaders` sends nothing when it differs from the row's URL, so a URL that changed without the values (an older replica during a rolling deploy, a rollback, a manual SQL edit) drops the event instead of sending the secret to the new URL, and keeping a value needs the stored `url`, not only the row's. A `null` key matches a stored name in any letter case, in both the keep lookup (`toStoredHeaders`) and the binding check (`assertUrlChangeRebindsStoredHeaders`): make one case-sensitive without the other and a case change either loses the value or carries it to the new URL. For the same reason `POST /test` takes no `destinationId` (an unknown key is stripped, as it always was, so old callers keep working) and rejects a `null` header — it can only send what the caller typed.
- **Delivery and `POST /test` read only the status of the response.** `safeHttp.postForStatus` takes the body as a stream without decompression, reads at most 16 KB of it to the end so the keep-alive socket goes back to the pool, and destroys it past that or at an `AbortSignal` deadline. The axios defaults buffered and inflated the whole body (a 200 MB answer added ~690 MB to the API), and axios `timeout` only fires on an idle socket, so a byte-a-time drip held the request open. Do not go back to `safeHttp.axios.request` here. `POST /test` answers an `errorCode` (`EventDestinationTestError`), never the raw error text, which held the resolved private IP and the `AP_SSRF_ALLOW_LIST` hint; it allows 20 calls a minute per user.
- **An update is a partial patch: an omitted field keeps its stored value.** `url` and `events` are optional on `POST /:id` and `PATCH /:id`, like `enabled`, `format` and `headers`, so the listing's Enabled switch sends only `{ enabled }`. It used to send the whole cached row, and a stale row wrote back an old URL and events plus `headers: null`, which deleted a header added in another tab without an error. Both checks run on the resolved URL (`url ?? stored.url`, read under the row lock), never on `rest.url`: compare `rest.url` and every toggle on a destination with headers answers the rebinding 400 (`undefined !== stored.url`), while a `format`-only switch to `OTLP_PROTOBUF` on a webhook URL slips through (`new URL(undefined)` reads as "not a webhook"). `headers: null` still means "clear all", so a client that echoes a cached row's headers deletes values it never saw. An unreadable stored map counts as no headers: a toggle leaves it alone, and a save that sends `headers` replaces it.
- **The delivery owns the framing headers.** `Content-Type`, `Content-Length`, `Content-Encoding`, `Transfer-Encoding`, `Host` and `Connection` are refused as custom header names in any letter case (`formErrors.reservedHeaderName`), and so are two names that differ only in case (`formErrors.duplicateHeaderName`). The format decides the body encoding, so a custom `Content-Type` could only mislabel it. Every send path also spreads the custom headers first and sets its own content type last.
- **An internal handler flow gets the custom headers, with lowercase names, exactly as an HTTP delivery would.** A handler flow whose Catch Webhook trigger uses HEADER or BASIC auth reads `payload.headers`, and the same flow reached through the embed-domain URL already gets them over HTTP. The consequence: the values enter the webhook job and the flow run's trigger output, which project members can read, the same as any HTTP request to that webhook. `POST /test` forwards the typed headers the same way.
- **An OTLP destination URL is used exactly as pasted.** The OTLP spec says a signal-specific endpoint "MUST be used as-is", and vendor paths differ (`/v1/logs`, Loki `/otlp/v1/logs`, PostHog `/i/v1/logs`), so nothing appends `/v1/logs`. The Connection step only warns when the path does not end in `/logs`.
- **Datadog, Dynatrace, and Elastic document protobuf only** for OTLP logs, so `OTLP_PROTOBUF` is the default when an admin picks OpenTelemetry. Datadog's AI assistant claims `http/json` works, but its source page is about the Datadog SDKs exporting to a local Agent, not the agentless `otlp.<site>` intake.
- **The worker encodes protobuf, not the API**, because BullMQ stores job data as JSON and raw bytes do not survive the queue. The queued payload is always the OTLP/JSON object; `contentType: 'application/x-protobuf'` on the job tells the worker to encode it. A job without `contentType` posts JSON, which is exactly the pre-format job shape.
- **The API refuses `OTLP_PROTOBUF` for any webhook URL** (400, `EVENT_DESTINATION_FORMAT_NOT_SUPPORTED_BY_WEBHOOK`), on create, on update and on `POST /test`, so a test cannot pass where delivery would fail. The webhook routes have no protobuf parser, so an HTTP POST of protobuf gets a 415, and the internal dispatch would hand the flow JSON anyway. The check uses `extractWebhookFlowIdCandidate`, host-agnostic like the cycle guard, so an embed-host URL is refused too. `OTLP_JSON` stays allowed: both paths deliver it as JSON.
- **The worker calls `resolveEventDestinationHeaders` only for a job with `hasHeaders: true`.** A destination with no stored headers (every pre-format destination) posts exactly as before, with no RPC to the API and no new way to fail.
- **A handler flow expects `RAW`.** Generate handler flow sets the format to `RAW`, because the generated router branches read `body.action`. A handler flow on `OTLP_JSON` gets the OTLP/JSON object, and its routes will not match; the OpenTelemetry step warns about this. `OTLP_PROTOBUF` never reaches a webhook URL: the API refuses it, and the OpenTelemetry step disables Protobuf and switches to JSON when the pasted URL is a flow webhook (`destinationFormUtils.isWebhookUrl`, the same host-agnostic path match as the server). It switches back to Protobuf only after its own automatic switch (`destinationFormUtils.resolveOtlpFormat`), so a JSON choice the admin made stays.
- **The form's header rows are a react-hook-form field array of `{ name, value }`, never a record.** They become a record only in `toHeaderRequest` / `toTestHeaders`. A blank value means "keep the stored value" only when the row's name matches a stored name in any letter case, the server's own rule; every issue goes on `headers.<i>.name` or `.value`, and the URL field carries `rules.deps: ['headers']` so the re-entry message shows the moment the URL changes. The old `DictionaryInput` folded rows into a record (last key wins): exact duplicates merged silently, and a new value next to a blank copy of a saved header sent `null` and kept the OLD secret.
- **The listing's Enabled switch sends only `{ enabled }`.** The collection's `onUpdate` posts `mutation.changes`, never the cached row, and the edit page refetches before it fills the form (`useFreshDestination`, comparing the query's update counters). The collection's private `QueryClient` is mounted while the live hook runs, so focus and reconnect refetch; nothing else would. It sets `retry: false`: with the default three retries a failed first load held the skeleton for about seven seconds before the error state and its Retry button.
- **The test card shows a result only while the form still matches the request that produced it** (`isSameTestRequest` against the mutation's `variables`), and its mutation sets `onError` in the `useMutation` options so a 400 shows in the card instead of the global "Something went wrong" toast.
- **The OTLP attribute keys are a customer contract.** Envelope fields keep their RAW names, and `data` is flattened to dotted keys (`data.flowRun.status`); the body is the raw event JSON, not evlog's wide event. `packages/server/utils/test/otlp-logs.test.ts` pins the whole request, so an evlog upgrade that changes `toOTLPLogRecord` fails a test instead of silently changing every customer's dashboards.
- The old `assertUrlIsExternal` check was **removed** to support internal handler flows; recursion is instead prevented by a server-side **cycle guard** keyed on the target flow of any webhook URL, regardless of route suffix (so a self-targeting `/draft` destination is still dropped on its own run events).
- **The cycle guard is host-agnostic on purpose — do not "tighten" it back to an origin check.** It matches any destination whose path contains `/v1/webhooks/<flowId>`, percent-decoding the id segment. It used to require `destination.origin === getPublicApiUrl().origin`, which is `AP_FRONTEND_URL`: platforms with an embed subdomain get `WEBHOOK_URL_PREFIX` rewritten to `https://<embed-hostname>/api/v1/webhooks`, so the origin never matched, the guard failed open, and a handler flow re-triggered on its own runs — one webhook POST produced 838 runs in ~3 min (GIT-1641, Pylon 5378). `domainHelper.getPublicApiUrl()` is called with no `platformId` here, so it can never resolve to the embed host. The path is the stable part (`/v1/webhooks` is fixed by the route registration and every URL builder); the host is not.
- **When the guard fires it drops *every* webhook-shaped destination for that event, not just the self-target.** Exact-match filtering would let two flows wired to each other ping-pong forever — destinations are platform/project-scoped, so the mutually-wired pair both sit in the same candidate list. The cost is that genuine cross-instance chaining (a destination pointing at *another* instance's `/v1/webhooks/...`) is also dropped for the looping flow's events; the `droppedDestinations` field on the cycle-break `warn` is how you see that happened.
- **Still-open loop:** two flows wired via *different* event actions (X→Y on `FLOW_RUN_STARTED`, Y→X on `FLOW_RUN_FINISHED`) never put an emitter-targeting destination in the same event's candidate list, so the guard never fires and the loop survives. URL matching cannot close this; a hop/depth counter on the dispatch chain would.
- **Three URL parsers coexist with different semantics** — `matchInternalWebhookFlowId` (origin-strict, prefix-based, does *not* percent-decode), `extractWebhookFlowIdCandidate` (host-agnostic, marker-based, decodes), and `webhookRouteSuffix`. They can disagree on the same URL. Dispatch classification stays origin-strict deliberately, so cross-instance chaining still delivers over HTTP outside cycle events.
- Frontend uses a **TanStack DB live collection** (optimistic local mirror + `useLiveQuery`), not standard React Query.
- A one-click "Generate handler flow" builds a webhook-triggered flow with per-event router branches.

### Key files
Entry point: `eventDestinationService`, a log-scoped factory wired up in `platform-webhooks.module.ts` under the `/v1/event-destinations` prefix.

- `packages/server/api/src/app/event-destinations/` — the service (trigger, internal vs external routing, cycle guard) and the typeorm entity
- `packages/server/api/src/app/ee/platform-webhooks/` — the HTTP controller and module that expose the endpoints
- `packages/server/worker/src/lib/execute/jobs/event-destination.ts` — worker side of the BullMQ job, POSTs external destinations via safeHttp and encodes protobuf
- `packages/server/utils/src/` — `otlpLogs`, the OTLP/JSON builder and the inline protobuf descriptor (field numbers from `opentelemetry-proto` v1.11.0)
- `packages/core/shared/src/lib/ee/event-destinations/` — request/response zod schemas and barrel export
- `packages/core/shared/src/lib/ee/audit-events/` — the `ApplicationEventName` enum plus `buildMockEvent()` for test deliveries
- `packages/web/src/app/routes/platform/infra/event-destinations/` — the listing tab, the three-step destination form (Destination, Events, Connection), its TanStack DB collection, and the handler-flow builder
- `packages/server/api/test/integration/cloud/event-destinations/` — integration tests covering CRUD and trigger dispatch
